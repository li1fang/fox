### 状态定义

- `软件验收通过`：有指定软件测试结果，但不代表已接入 App、真机产品验收或云端上线。
- `设计记录已建立`：方向和待定项已落文档，不代表视觉定稿或功能完成。
- `设计预览已有`：可交互布局用于讨论；不代表 Figma、原生 App 或真机能力验收。
- `未启动`：只登记目标、依赖与验收点，本轮不实现。
- `暂缓`：没有当前实施承诺，必须有新的价值和范围决策才启动。

## 3. 三个级别的互联互通

沿用此前讨论的三种能力难度。它们不是“局域网 -> 家庭服务器 -> 云端”三个部署阶段，后者是可选传输/部署路径。以下是规划目标，不是已经实现或保证可用的能力。

### CON-01：记录和照片交换

目标：iPhone 或 iPad 的本地记录可以可靠地到达另一设备，离线时仍可独立保存。主要难点是附件完整性、重试、去重、修订冲突及删除传播，难度判断为中等，实际协议尚未定稿。

以下为互联讨论时的历史问题清单；SYNC-0–3 已实现的协议/墓碑/游标/设备认证以顶部链接为准，不把旧“未实现”描述当作当前状态。完整备份与增量同步仍是独立契约，备份不会克隆配对凭据。

待设计内容与验收点：

- 稳定记录 ID、来源 ID 与内容修订分开；附件校验后才宣布目标端可用。重复传输不重复记录、不覆盖较新更正。
- 同时编辑、离线删除与另一端编辑必须有显式冲突方案；重新连接不能复活已删除记录。未来删除传播机制须专门设计，不能假定当前硬删除已支持。
- 中断、损坏、重复投递、错误对端、未授权设备和网络切换都有自动测试；明确区分“已存本机”“等待传输”“对端已接收”。
- 保留身份认证、授权、加密传输、撤销设备与敏感数据处理的决策，不将 LAN 或同名设备当作可信身份。

路径候选：同一 Wi-Fi 直连优先评估；家庭 Mac/Linux 服务可用于中转和备份；云端用于外出及异步同步时需单独评估账号、费用、隐私与运维。文件导出/AirDrop 导入仅是手动迁移路径。Bonjour / Network framework 是此前候选，尚未选为最终协议；使用前复核当前官方 API 与系统能力。

2026-10-17 FIT-DIAG 补记：诊断文件先采用 UUID 清单、逐文件 SHA-256、私有暂存、校验后原子接收与幂等重试；可以为未来大附件交换积累契约经验。开发期使用已配对 CoreDevice 显式拉取，不是已实现 App 间直连/云同步、后台发现或大文件断点续传，CON-01 状态不因此改为完成。

免费签名、系统 entitlement 和账号能力可能约束 CloudKit 等路径，启用前再核实，不把免费账号可用云同步当作前提。本轮不申请新账号、不购置云服务、不修改局域网或远端配置。

### CON-02：训练观察端与交互端

目标：初始角色建议 iPad 观察和计数，iPhone 查看状态、提交反馈与控制操作；角色分工可在后续计划中调整。主要难点是状态一致和断线恢复，难度判断为中等。

原则与验收点：

- 只有一台设备主持训练状态机并保存权威记录；另一台提交带稳定 ID 的命令，收到明确确认才显示成功。
- 只传次数、阶段、追踪状态和命令，不要求传实时视频、音频或逐帧骨架。观察端计数和本地记录不依赖链路持续可用。
- 首版按双方 App 前台使用设计；后台、锁屏或断线时明确降级，不能悄悄继续把过期状态当实时。
- 重复、延迟、乱序命令，以及连接到错误训练会话都必须拒绝或幂等处理；重连先获取当前快照，不盲目重放旧“下一组”。
- 断线期间的停止、暂停和本地纠正以主持端为准，不能因远端命令覆盖更新结果。软件故障注入和双机真实断线验收分别保留。

可与 CON-01 共享传输设施，但记录同步成功不代表实时训练控制正确；也不要求先完成云同步才研究受限 LAN 协作。

### CON-03：多摄像头或深度融合

目标仅作研究储备：两机同时观察、融合深度或三维动作评价。它与“另一台只显示次数”不是同一个任务。

难点包括机位标定、时钟与帧对齐、主体关联、遮挡、不一致观测、性能和数据隐私。能拿到深度不等于深度对计数有帮助。本轮不开发 LiDAR 融合、TDPT、实时视频串流或通用动作质量评分。

启动条件：先选一个现有二维方法确实无法解决的问题；提出有限样本、可复现的对照实验和停止条件，证明收益值得额外复杂度，否则继续暂缓。

## 4. 记录、存储之后的分析

分析是新增的派生层，不是给 `CaptureRecord` 随意塞几个 AI 字段。当前记录 Schema 是闭合契约，未来事实、模型输出和审核状态应有独立的版本化契约，并明确与原记录的关系；本轮不建这些表、不更改现有 Schema。

### ANA-01：事实草稿与人工核对

一条原始记录可以对应多个事实，但每个事实都需要证据引用、状态和来源。候选类别包括购买、消费金额、食用、身体感受、起床，以及外部导入的测量；保存原始记录不等待提取完成。

待定契约至少考虑：原记录 ID 与修订号、相关文字或图片证据、事实类型、数值与单位、发生时段、来源类别、是否用户确认，以及提取器/模型/提示版本。模型的置信声明不等于经校准的准确率。

例子和边界：

| 原始输入 | 允许形成的草稿 | 不允许悄悄补全 |
|---|---|---|
| 起床了，感觉头疼 | 起床事件、主观身体感受 | 精确开始时间、疾病诊断 |
| 买了两块羊排，400 克，80 元 | 购买、数量、支出；币种未知时保留未知 | 已吃完、摄入热量、自动猜币种 |
| 吃了昨天买的一块羊排 | 食用事件、待核对的购买关联 | 仅凭照片精确推定重量、把剩余库存当作已确认 |

用户更正后保留原证据与修订关系。原记录修改会让旧派生结果变为待复核；原记录删除后的派生内容、缓存和外发处理需专门定义撤销/清理策略，不能只删首页卡片。用户拒绝的事实不应在后台反复自动恢复。

自动测试目标：同一提取任务重试不重复事实；一个输入多事实；缺失信息保持未知；改原文后旧结论不能继续伪装成当前；拒绝、确认、更正和删除均可追踪。先用合成输入和确定性 stub 验证契约，再选真实 provider 和开展独立质量评测。

### INPUT-01：外部测量不是照片分析

步数和活动能量属于外部测量导入，不要求给它伪造留言或照片。需保留 provider、来源记录 ID、测量时间区间、单位、授权和来源去重；不同设备或平台的重复覆盖不能直接相加，时间区间跨天要明确定义。活动能量不是仅走路的热量，也不等于包含静息代谢的全天总消耗。

优先评估 iPhone 上只读 HealthKit 的 stepCount / activeEnergyBurned，不在本轮读取权限或设备数据。无权限、无数据、零值三者不同；接口不保证能区分拒绝读取与没有数据，不能凭空结果宣称有权限或显示零。旧数据更正或来源撤销不能继续以旧总数展示。账号能力、签名与授权在实际启用时复核；此项不阻塞 M2，也不启动有氧视觉。

### ANA-02：选择一种跨记录问题

不是一开始同时做营养、价格、库存、睡眠和训练策略。后续从以下场景选择最有价值的一项：

- 营养估算：区分用户填写、外部数据库和模型估计，缺重量时保留范围或未知，不把照片预测当测量值。
- 价格比较：统一数量、单位、商品条件和币种后再比，不把总价不同直接解释成变贵；没有可比历史时不生成确定结论。
- 购买与食用关联：允许询问“前几天买的是否吃了”，不能因三天没记就断言未吃、变质或仍有库存。
- 活动与摄入回顾：结合可信步数/训练和饮食记录，但必须显示数据缺口，未记录不等于没有发生。
- 健康感受回顾：按时间呈现用户的感受变化与来源，不给疾病诊断或自动用药决定。

所有分析结果应携带证据引用、有效时间/数据范围、算法版本及不确定性，可以重算、撤回和人工修正，不覆盖原文。能在本地数据上开展的分析不必等待互联完成；第三方 AI 外发需明确数据范围和用户选择。

### ANA-03：分析输出与主动建议

未来输出可以是一张分析卡、从记录发起的对话、周期复盘或提醒，不预设纯聊天首页。呈现区分“原始记录”“用户确认”“模型估计/建议”，点击可追溯到依据。

提醒需定义触发理由、重复抑制、用户关闭/纠正、时效和停止条件；先在 App 内验证，不默认增加推送或计划任务。不自动做医疗、用药或财务操作，也不依分析直接改变训练计时器或训练状态。

### FOLD-IOS-01：首选后续验证方向

- 目标：在选定设备的展开、合拢与悬停状态下，完整显示相机、清晰呈现当前组/次数/节奏，并在形态切换时保留训练及人工记录；先比较是否减少摆放和中途操作负担。
- 没有 Duo 真机不阻塞后续静态/交互布局、窗口变化、合成相机中断及状态保存测试。真实相机选取、内外屏切换、镜头画质/视场、持续负载与现场计数另列待验收，不能用模拟器结果代替。
- 不预设悬停一定优于普通设备加支架。对照记录摆放耗时、可见关节、训练距离下的可读性、需要接触屏幕的次数和状态中断；没有明显收益可继续暂缓。
- 相机俯仰、屏幕倾角、铰链角度是不同量。现有单块设备的 Core Motion 推导不能未经验证用于折叠设备两半屏幕和不同镜头；未来先明确传感器参考系及缺失语义。
- 启动前确认目标 SDK/模拟器、可执行范围和真实设备验收的取得方式；无设备时允许交付“布局候选”，不写成“Duo 完美支持”。这是平台扩展内的第一顺位，不高于当前 FIT-LIVE-R1。
