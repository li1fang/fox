## 本轮结论

**未完成根因修复，完整验收仍阻塞，B 不实施。** 仅有执行器的快速失败防线通过验证；不能把它叫作动画问题已经解决。

证据将问题缩小到当前 Xcode 27.1 / iOS 27.0 的 SwiftUI 输入与 XCTest 动画空闲同步组合：

- 原备份测试在输入完成后发生等待。画面文字完整，Fox 主线程采样处于正常空闲；临时公开 CALayer 观察器仍持续写出数据。
- 对照中主动收起键盘后，窗口树已没有动画，自动化仍等不到完成通知。系统日志能看到 main-run-loop idle 回复，却缺少对应 animations-idle 回复。这不等于证明所有系统内部动画都已结束，也不等于已找到 Apple 内部错误代码行。
- 不含 Fox 代码、数据库或训练逻辑的独立小应用也复现：UIKit 文本页 5 次通过；SwiftUI 多行输入页出现相同 60 秒等待。最小程序初版另有结果页捕获旧值的样本缺陷，已在后续对照中改为 Binding；该样本缺陷不解释发生在输入阶段的等待。
- 修正结果绑定，并把交互式收键盘改为立即收起后，SwiftUI 前 3 次通过，第 4 次仍在打开结果页后等待 60 秒。不能为此修改 Fox 的收键盘交互。

分类：环境/框架交互已有独立复现；内部生命周期细节仍未知。UIKit 的 5 次通过只是对照，不证明 UIKit 永远不会出现同类问题。没有证据指向 Fox 的计数、存储或训练计时逻辑，也不据此判断真人使用中一定发生同样问题。

### 结果：重启没有解除门禁，但两个状态报告不一致

- 约 **96 秒**完成一次首次启动、一次正常 shutdown/boot 及清理；两阶段设备 ID 相同。原首次失败及此前所有回执保留，没有重建、擦除或追加重试。

Migration not necessary`，backboardd 报告 `Data migrator was not necessary` 和 `Data Migration ready`。warm 日志获取窗口为最近三分钟，会混入首次启动；`restart-analyze.mjs` 按 warm boot 命令的实际开始时间过滤，避免误把旧 incident 算成重启时的新错误。该时间窗未见新的 progress-window failure 行，但仍有 unsupported screen class -1。

## 输入动画生命周期取证及采集器失败

### 方案与可判定边界

旧 `animation_trace.py` 在附加时只查一次计数符号；当时框架未加载、断点位置为零，随后断点自动绑定，但计数地址仍为空。旧寄存器 x0/x2 的名称也没有对象身份依据，不能将其直接用于动画实例配对。

本轮方案改为：在实际计数增减方法触发时延迟查找 `XCTActiveAnimationsCount`；记录 32 位计数、线程、时间、调用栈和模块地址，核对相邻事件的计数连续性。只读查看已安装框架的反汇编，确认增减方法使用原子加减；不硬编码地址，不调用目标方法，不改内存或禁用 idle。框架二进制与运行时注入版本可能有地址差异，必须动态解析。

先写八项账本测试，覆盖完整平衡、剩余来源、混合来源、缺读、跳变、非零起点、末值不一致和空证据。通过后才开始 live batch。来源净增减不是对象级生命周期：只有记录连续、起点明确，才能讨论哪些调用路径留下计数；不能据此命名“具体哪两个动画”。调试器会改变时序，成功回放也不是性能或修复验收。

契约 `LIFECYCLE_CONTRACT.md`：仅原 iPad/27.0 组合，一台自有模拟器、一次启动、零重启；原 `SplitTests/testInputOnly` 不变，最多八次、首败即停；测试五分钟，整轮八分钟加清理；每 PID 调试器 85 秒外层上限、2500 事件上限，内盘小于 2 GiB 停止。采集器自身故障同样停止，不继续几何或全量。

### 实际结果：采集器缺陷，不是产品失败

- iPad 启动门禁通过，没有继续处理 Duo 初始化，也没有环境变更。
- 首个计数方法触发后，动态符号地址确实解析成功。但 `emit(kind, **values)` 同时接收到位置参数 `event` 和关键字参数 `kind=start`，抛出 TypeError。错误来自 Agent 编写的采集代码。
- 断点回调异常让目标停住；85 秒外层限制终止该采集，执行器随后中断 XCTest 并释放自有资源。整轮约 **213.2 秒**，只有第一轮开始，零输入值断言通过、零有效生命周期事件，没有原 `App animations complete notification not received` 故障证据。
- 因此自动化会话及输入前的异常长等待已被采集器污染，不用于分析原故障，也不把停止算产品测试失败。suite 为 failed（collector），不是绿色或八轮完成。

### 已修什么，尚未验证什么

保留原 `lifecycle_trace.py` 和失败回执，另存 `lifecycle_trace_v2.py`。新增五项直接调用实际 Python 回调的测试：事件序列化、完整 start/stop 回调、回调异常转为故障并返回继续、符号延迟解析、内存读取失败不伪装为零。旧采集器其中三项报错，修正版五项通过；连同八项账本测试，共 **13 项离线测试通过**。

修正版改用不冲突的 `event_type` 参数，并捕获回调异常、记录后返回 False，避免 Python 异常把目标留在断点；补墙钟时间，断点回调模块名动态取自身。**修正版未再运行模拟器，原运行器仍保留失败时的 v1 引用，下一次必须明确接入 v2，不能直接重用旧命令声称已修好。** 本轮不追加第二次启动。

方法反思：先前只测了下游账本判定，却没有在运行前调用一次真实采集回调，这是可避免的验证缺口。后续先完成“采集回调 → JSON → 账本”的离线链路及故障退出测试，再准入有界运行；尤其要把采集器错误与目标应用错误分离。此次没有足够证据选择产品修法，也没有找到原先两个未结束动画的身份。

本地证据：`lifecycle-input-ipad/` 保存 suite、完整日志、trace 错误及中断结果；`lifecycle-analysis.json` 明确标记零事件/不完整；`lifecycle-static-disassembly.log` 保存只读指令证据；`lifecycle-preservation-before.json` / `lifecycle-preservation-after.json` 核对原始 1038 项文件与资源状态。下一步是修正版采集器的有界有效性验证；若取得完整且重现原故障的计数链，才依据来源决定修复方向，否则保持“未定位”，不再调整产品 UI 或轮换参数。
