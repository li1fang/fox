# D1-CLOSE-R1：零次与未知的核心消费契约

2026-10-29。视觉与训练核心负责；基线 `1113355d1824493e6872c15fad056646ff023dd1`。客户端集成、共享 CURRENT/台账由各自 owner 处理。

## 编辑前测试设计

目标：阻止处理帧大于零自动成为可预填零次，保留已接受非零次数与未知阶段的独立性；新保存记录不把人工填写零次升级为视觉确认。先用现有 UI 预填表达式及实际 TrainingSession 保存调用证明反例，再实现窄核心 API。

六类：纯准备失败（禁止更新、无预填）；正式开始后全无效；短暂有效后丢失；连续有效但未接受完整动作；未完成动作/中断恢复；非零但完整阶段未知。各类检查原始观察、预填、保存/重载和计数来源；额外保护旧零次档案与未知策略版本。原计数/返回测试继续通过。

不改动作阈值、计数器、相机、UI、CI、设备、原件或私人库；不用秒数或 validFrames>0 推导可用覆盖。现有汇总没有足够证据肯定有效零次，因此所有自动零次保守不预填，人工仍可明确确认零。

执行：复用维护树 RES native-resource 包装叶级 Swift，Node22、Xcode27.1、jobs2、外盘独立缓存和回执。红/绿均保存；资源冲突/输入变化/工具链缺失停止相应执行，不抢占。测试必须在 catalogue 登记；不跑整套 UI/动画等待。新字段须向后兼容，旧计数来源不能被重新解释后判坏档。

公开样本只读窗口：沿既有接收结果评估时间映射；若不足以解释准备/保存，用合成契约反例补齐，不假称为视频端到端验收。

## 已证实的问题与最小 API

基线 TrainingScreen 使用 `hasObservedFrames ? automaticCount : nil`。六类反例实际运行，纯准备失败与非零/阶段未知通过，其余四类产生8条失败：预填为0，人工确认后标成 vision_confirmed。先前两次测试夹具编译错误（误用 TrainingSession.validate、替换范围误及旧断言）保留；它们不算产品红灯，修正夹具后才记录上述行为红灯。

`WorkoutVisualEvidence.suggestedCount: Int?` 是客户端唯一的自动预填入口：已接受非零次数返回数值，其余返回 nil。`automaticCount` 和 `hasObservedFrames` 保留原始含义，用于说明处理事实，不作覆盖充分或可置信零次判断。即使所有帧的局部关节有效，也不从汇总证明连续可用零次；这不是否认用户可以实际做零次。

客户端接入：反馈页只在 suggestedCount 非 nil 时预填对应侧；nil 保持未填写并提示核对，不将其变成0。已存人工草稿仍保留；观察0与用户确认0分开。非零伴阶段未知或中断时，次数保留，仍显示已有的阶段/覆盖欠项。纯准备失败不能写入处理帧、不能启动训练时间。

新视觉记录写 `countingEvidenceVersion=1`。无已接受次数的观察，在用户明确填写零或非零后均记 manual_with_visual，原视觉0与用户次数分别保留。非零的 vision_confirmed/vision_corrected 与现有 fallback 路径不变。缺版本的历史记录按原规则校验；不重写其原来源声明，也不把它当新零次规则已验证。未知版本拒绝。新旧应用混用的读取兼容未验收；旧应用没有这项判定，不应作为新记录的回退读者。客户端须采用本提交并验证集成后再交付。

客户端集成期间，数据线审查发现未知版本校验原仅位于有 visualEvidence 的分支，纯人工记录携带版本 2 可漏过。新增无视觉版本反例已先证明失败；支持版本校验移至每条记录的公共校验路径。缺字段旧档仍兼容，已知版本 1 且无视觉证据允许读取且仍为 manual，不因版本标记补造视觉证据；新产生的纯人工记录仍不写该字段。此补丁不迁移／重写旧档，也不构成旧应用读取新记录的兼容验收。
