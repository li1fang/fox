# M4 现场视觉复盘：存在，但不可用

日期：2026-10-17。结论：用户本轮现场可用性验收不通过。仅取回数据、检查代码和数值回放；不改计数算法或设备配置，不安装新版本，不把此次短测试称为完整训练。

## 现场反馈

用户表示需要小心配合才能偶尔计数，未看到录像校准带来的可用改善；手臂可见时也可能无法启动。用户随后明确“测评局”是侧平举，完全无法开始计时；没有保存对应报告，不据此补造侧平举记录或次数。

## 本轮实际证据

从同一 iPad Fox 容器只读复制到私有 `.tmp/fitness-review-20261017-newtrial/`，视觉报告由 6 份增为 9 份。新增均为 `source=camera`、Fox 0.4.0、`curl_2d_v3`，没有新增侧平举报告。以下时间为 Asia/Bangkok。

| 报告 ID 前缀 / 开始时间 | 所选侧 | 自动次数 | 有效测角帧 / 处理帧 | 中断数 |
|---|---|---|---|---|
| 3CFDA498 / 04:49:04 | 左 | 0 | 197 / 495 | 9 |
| 7C6AEE73 / 04:50:58 | 左 | 5 | 431 / 546 | 7 |
| 082CA1DE / 04:52:33 | 右 | 4 | 239 / 281 | 4 |

三份均没有 `referenceCount`，因此 5 和 4 不是准确计数的验收结论。指标中的有效帧数来自控制器测角检查；不能与计数器 trace 的 `quality=valid` 简单等同，两者还存在角度跳变等后续检查。

处理约 10 Hz，单帧 Vision 处理 p95 约 12.5–12.7 ms，热状态 nominal；未见这些指标指向算力或热压力，但它们不是完整端到端时延或关节识别质量证明。

已核对恢复安装包中的两份默认参数资源与当前源资源逐字节一致。新报告也冻结了新 runtime policy：启动缺失容差 0.35 秒、放低阶段容差 1 秒、返回容差等。基础配置名仍为 `reliability-candidate-v2`，不表示实际算法退回 v2。问题不能先归因于没装上校准版本。

执行 `npm run vision:replay -- .tmp/fitness-review-20261017-newtrial/vision-trials.v1.json` 成功；三份新报告的次数与逐次数据均被原参数重现，分别 0、5、4。日志 `.tmp/fitness-review-20261017-newtrial-replay.log`。这证明失败行为可复现，不证明现场准确或可用；回放输入是已选主体的数值轨迹，未重跑原始图像识别和主体获取。

## 已定位的规则与缺口

1. **启动并不要求全身。** `PoseSubjectSelector` 先选择主体：可见肩部均值须在归一化 x=0.25–0.72、y=0.50–0.95 的获取区域（y 原点在图像下方），置信度至少 0.35。之后只要求所选侧肩、肘达到 0.35，稳定至少 0.25 秒再倒计时 3 秒；短缺失超过 0.35 秒或相邻处理帧超过 0.40 秒会重置准备。脚、膝、双臂齐全都不是启动硬条件；近距离、出界、所选侧或识别缺失是否导致这次失败，尚无准备阶段轨迹可确认。
2. **启动、骨架展示和测角采用不同条件，界面没有清楚区分。** 弯举计数需要所选肩、肘、腕；侧平举还需同侧髋或受约束的新鲜对侧躯干参照。看见骨架或肩肘不等于已选中主体、能启动、能测角，更不等于达到计数端点。
3. **主体丢失后的锁定会阻断后续计数。** `PoseSubjectSelector` 超过 1.2 秒未匹配后进入 `lost`，不自动重新绑定，必须明确重新就位。这原为防止路人接管，但恢复负担过重。第一份约 34.8 秒起进入 `lost`，余下约 14.7 秒保持该状态；整份有 77 帧原画面检测到人、却未选出主体。不能将这些帧统称为 Apple Vision 没检测到人，也不能断言全部为同一个人。
4. **还有基础关节和测角不稳定。** 第一份有大量低置信度、角度跳变和缺失；右侧有两次 `movementTooShort` 拒绝，只代表可靠观测时间没达门槛，不等于用户实际做得太快。没有本次视频与人工逐次标签，不能确诊每一次拒绝是漏计还是合理拒绝。
5. **失败启动没有完整报告。** `trialStartedAt`、计数 trace 和机位采样只在 `beginCounting()` 后建立，`saveReport` 又要求该时间存在。因此从未完成倒计时的尝试不能正常形成完整报告；实时状态也缺少完整准备状态与逐条件阻塞原因。没有新增侧平举报告不能推断没尝试。
6. **录像验收绕过了关键现场环节。** 已有视频的轨迹计数刻意绕过启动倒计时；Mac 提取的同一开发视频不是独立样本，也不是 iPad 相机图像。原回放结果保留，但不足以证明机位、获取、启动和丢失恢复已可用。

代码定位：`PoseRuntimePolicy.swift` 的 `PoseSubjectSelector`、`PoseStartGate.swift`、`VisionLabController.swift` 的 `beginCounting/receive/saveReport`，以及 `PoseTracking.swift` 的几何检查和循环状态机。

## 建议下一步，待讨论后实施

- 先保护真实训练：计时、节奏演示和人工记录不以视觉成功为必选前提；保留视觉就位模式，同时有明确的人工开始/回退。识别缺失不清零已确认次数、不替用户结束训练，视觉故障与疲劳/动作问题分开记录。
- 补失败可观测性：从点击开始就建立有界诊断，记录候选版本、动作/侧、主体获取、所需点可见性、倒计时重置和恢复事件。取消/超时也能保存失败报告；不默认录像或采集人脸。准备阶段与正式训练时间分开。
- 降低获取和恢复操作负担：提供实际阻塞原因与明确恢复路径。是否自动重绑须保留防路人接管、多人歧义和半次丢弃约束，不能只无限放大容差或自动换人。具体策略尚未批准。
- 在现有素材上检查 iPad 完整图像处理路径，再与 Mac、主体选择和数值计数分别比较；显式检查是否完成启动，以及静止、半程、遮挡和中断窗口。原始录制文件与实时前摄仍有差异，素材 manifest 未确定镜像和设备倾角；设备文件回放通过也不能替代最后的小范围现场验证。
- 下一轮软件测试先覆盖近景/缺髋启动条件、肩部获取区域边界、始终未就位可保存、倒计时重置可解释、丢失后恢复、多人拒绝及人工回退；保留旧视频负例和既有数据。通过后只做一次小范围真实验证，不强迫额外运动或扭曲动作迎合计数器。

不扩大到新动作、动作标准性评分、深度、多设备或实时语音。该方向是“先让训练能用，再验证视觉能否帮忙”，不是继续以单条视频总数作为产品完成标准。
