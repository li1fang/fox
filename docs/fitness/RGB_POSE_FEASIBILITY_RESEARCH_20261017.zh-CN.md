# RGB 健身计数：可行性、参考实现与验证建议

日期：2026-10-17。范围：查阅官方文档、官方源码/样例、研究实现及少量社区项目，结合 Fox 当前源码和现场失败证据分析。没有在 iPad 上跑新模型、没有新增依赖或修改算法；下述比较是建议实验，不是已完成的性能或准确率结果。

后续用户批准开始实验：[V1 Mac 离线结果](experiments/RGB_COMPARISON_V1.results.zh-CN.md) 已单独留证。下方保留实验前研究判断；新结果没有显示替换 MediaPipe 的计数收益，Apple 时序计数亦不能直接替代。M4 同视频和实时场景仍未完成，不把 Mac 结果补成真机通过。

## 1. 结论

**不能据目前失败认定 RGB 前摄不具备计数能力，也不能认定继续调 Apple Vision 的阈值就一定能成功。** 当前明确同时存在产品门槛、主体恢复和几何可观测性问题；需要分层测量。

推荐保持单设备 RGB，优先做一次有限的 A/B/C 技术比较，同时让原训练计时和人工记录不受视觉成败阻挡。先不投入深度、多机、模型微调或动作质量评分。两动作均无法在普通机位获得有意义收益时，将视觉保留为实验工具，主线回到训练记录和生活日志。

“普通机位”可以要求一次合理摆放、动作所需区域入镜和照明充足，但不能要求用户每次扭曲动作、反复正侧转身或调整多次才能数。是否愿意为视觉固定一个机位，是产品取舍，不应藏在算法成功率里。

## 2. 把诉求拆开

| 层级 | 本项目目标 | 不应混为一谈的内容 |
|---|---|---|
| 训练记录 | 正常开始、计时、结束、人工确认并保存 | 不是必须先通过视觉门禁 |
| 次数辅助 | 在支持机位识别该动作的往返事件；原始自动值与实际值分开 | 不是数屏幕节奏，不补造缺失段次数 |
| 节奏事实 | 观测可靠时给出上举/停留/下放时长，缺失则标估计/未知 | 不是仅凭 2D 位移输出真实米/秒 |
| 最低幅度 | 用已定义、可观测的端点判断是否计为候选完整循环 | 不是专业动作规范或安全性鉴定 |
| 动作质量 | 暂缓；以后每个具体维度独立验证 | 不把关键点置信度变成动作分或总分 |

弯举首先验证侧面或略偏侧、近镜头一臂可见；侧平举首先验证正面、肩肘和所需躯干参照可见。具体最佳偏转角尚无本项目对照，不宣称必须固定某个角度。手腕在身体前后方向移动时，正面二维肘角可因投影压缩和自遮挡失去信息；这是几何限制，不是提高模型置信度阈值能消除的问题。Google 也明确提示仅用 x/y 计算的角度随拍摄方向改变。[角度方法的边界](https://developers.google.com/ml-kit/vision/pose-detection/classifying-poses)

## 3. Apple Vision 能做什么

Apple 的 2D 姿态接口提供关节点和置信度，不自动给出运动语义或可靠的身份连续性。官方建议人至少占图高约三分之一，尽量包含主要身体区域，避免宽松遮挡和密集人群；已知 ROI 可以帮助估计。这是采集条件建议，不表示 Fox 必须以全身或双臂齐全作为启动硬门槛。[官方 2D 指南](https://developer.apple.com/documentation/vision/detecting-human-body-poses-in-images)

不能由“RGB”直接推出“只能检测静态骨架”：Apple 已有视频计数样例。但也不能由样例推断我们两动作在近景、遮挡和疲劳下已经可靠。

当前 Fox 约 10 Hz、Vision 单帧 p95 约 12.5–12.7 ms，只说明本轮未见这部分算力吃紧，不证明模型质量或端到端实时性。本轮 0/5/4 三份弯举报告没有人工真值；第一份约 35 秒后的主体 lost 锁定，是我们自己实现的连续性策略，不是 Apple Vision 宣布永久无法识别人。详见 [现场复盘](M4_REAL_TRIAL_REVIEW_20261017.zh-CN.md)。

## 4. 最值得比较的现成路线

### Apple Create ML Components：优先加入计数基线

`HumanBodyActionCounter` 是系统提供的时序计数组件，官方路线串联姿态提取、主体选择、滑动窗口与累计次数输出，不需本项目先训练专属模型。它计算重复运动，不等于通过 Fox 的幅度或动作质量要求。[WWDC22 官方实现讲解](https://developer.apple.com/videos/play/wwdc2022/10020/)

样例建议明亮、全身可见，支持前后摄；说明了采样率、慢动作降采样和窗口对效果的影响。结果可为小数，不能直接四舍五入成已确认完整次数。90 个姿态在 30 Hz 下约 3 秒，在 10 Hz 下约 9 秒；这只是窗口时间跨度推算，不是已测端到端延迟。必须实测慢速 2/1/3 节奏、暂停、变速、静止和半程，不能照搬示例设置。

来源：[官方计数样例及源码片段](https://developer.apple.com/documentation/createmlcomponents/counting-human-body-action-repetitions-in-a-live-video-feed)。本机 iPhoneOS SDK 的 CreateMLComponents.swiftinterface 已核实该类型自 iOS 16 可用，当前 Fox 源码未使用。系统组件不是完整开源模型，也没有在本轮被接入或跑分。

### MediaPipe Pose Landmarker：优先作为关键点替代基线

Google 官方提供 iOS 相机和视频处理源码、33 个关键点、visibility/presence 以及 Lite/Full/Heavy 模型。建议先比较 Full；只有实测表明质量收益值得耗时再加 Heavy，不将名称当作准确率结论。其视频/直播模式有追踪；时间戳、方向和异步忙时丢帧均需处理。[官方 iOS 接入](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/ios)、[Swift 相机与视频服务源码](https://github.com/google-ai-edge/mediapipe-samples/blob/main/examples/pose_landmarker/ios/PoseLandmarker/Services/PoseLandmarkerService.swift)、[当前模型列表](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker)

不能保证它一定优于 Vision。官方链接的 GHUM 模型卡（2021 年资料，不作为当前所有版本行为的完整说明）记录了对脸部位置、尺度、朝向、遮挡及照明的敏感性；其关键点评价也不是健身组准确率。模型推断的 z/world coordinates 不等于深度传感器测量或隐藏关节真值。[模型卡](https://storage.googleapis.com/mediapipe-assets/Model%20Card%20BlazePose%20GHUM%203D.pdf)

### Google ML Kit 官方计数例程：学习方法，不直接迁移全 App

官方 `PoseClassifierProcessor` 先做分类和平滑，再调用 `RepetitionCounter` 的不同进入/退出阈值，避免在边界抖动时重复计数；无姿态时不更新计数。可学习时序分层与迟滞设计，但 Fox 已有平滑、端点迟滞和短缺失容差，不能仅“再加一次平滑”就称为新方案。

该示例主要演示俯卧撑/深蹲分类；基于姿态样本的分类路线需要多样化样本，不是把 Fox 一段录像切成许多相邻帧就获得泛化。SDK 的关键点置信度、MediaPipe visibility 和 Apple confidence 语义不同，不直接套同一个数值阈值。[处理源码](https://github.com/googlesamples/mlkit/blob/master/android/vision-quickstart/app/src/main/java/com/google/mlkit/vision/demo/java/posedetector/classification/PoseClassifierProcessor.java)、[计数源码](https://github.com/googlesamples/mlkit/blob/master/android/vision-quickstart/app/src/main/java/com/google/mlkit/vision/demo/java/posedetector/classification/RepetitionCounter.java)

### 其他项目：参考边界

- [RepNet / Google Research](https://research.google/blog/repnet-counting-repetitions-in-videos/) 从视频重复模式计数，说明次数可以不完全依赖解剖角度；但它不是已验证适配 Fox 的原生实时完整幅度计数器，本轮不做模型转换或 Linux 依赖。
- [RepDetect](https://github.com/giaongo/RepDetect) 是 Apache-2.0 的 Android 课程项目，展示计划、计数、历史的闭环，也承认样本覆盖和相似动作问题。其 README 的准确性自述不是独立 iPad 评测，不建议整体搬运。
- [QuickPose iOS demo](https://github.com/quickpose/AI-PushUp-Rep-Counter-Demo-iOS-by-QuickPose) 可参考引导和计数反馈，但依赖 SDK key 与独立 SDK 许可；公开 demo 不等于整套识别能力完全开源或无长期成本，本轮不采购。

本轮查阅的项目未提供能直接证明“我们的 M4 前摄、两动作、近景和遮挡条件”可用的独立结果。选择依据应是同输入测量，不是星数、功能列表或 README 宣传。

## 5. 为什么之前录像没有带来明显现场改善

1. **没有训练 Apple Vision。** 此前工作主要是参数、主体选择和计数状态机修复；没有改变 Apple 关键点模型权重。调后处理不能保证把没识别出的腕肘变准确。
2. **只有同一段开发素材。** 录制机位、光线、衣服和动作相对固定，反复对它调整存在适配过度的风险。分段或随机抽相邻帧仍不是独立场景。
3. **测的是不完整链路。** 已有计数回放绕过启动，Mac 提取不同于 M4 相机；数值回放还从已选主体后的坐标开始。当前新增报告也没有未启动过程的完整信息。
4. **缺少能用于模型对照的失败图像。** 新现场报告可复现后处理失败，但不能据已被过滤的数值坐标重跑其他图像模型，或确诊每一帧遮挡类型。原录像仍有回归、负例和候选比较价值，不需要丢弃或重录整套。

## 6. 应采用的工程实践

这些是本轮结合资料和 Fox 缺口提出的设计建议，不冒充每项已被某个外部产品验证。

- 将图像采集、姿态模型、主体关联、动作事件、训练状态分别诊断；每层拒绝原因可追踪。普通用户看到针对当前阻塞的一条简洁提示，而非理解参数表。
- 统一实际输入图像、显示镜像、左右臂语义、横竖屏、宽高比和 ROI 坐标转换。先做转换回归，不能只凭骨架看起来接近来证明一致。可试带运动余量的主体 ROI，必须同时验证肢体不会被裁掉和丢失后能重新检测。
- 保留身份/动作状态连续性，但不把旧位置当新测量。短缺失有界恢复、长缺失丢弃半次；进入恢复时保留完整次数并明确提示。重绑候选仍需处理路人和多人歧义，不无限等待或静默换人。
- 按动作采用最少必要关节和可靠参照；不要为弯举强制全身，也不要为侧平举在两髋不可观测时伪造躯干。关节稳定性、时间跨度和幅度均单独记录，不因一个标签或单帧跳变判定用户动作错误。
- 现有训练人工开始/回退能力保留并做成清晰主路径；视觉模式的失败不应强迫用户回到屏幕摸索。研究页从点击开始就能保存失败准备过程，诊断有界，原始录像仅由用户明确选择导入/录制。

## 7. 建议的有限实验

最多三个候选，先用私有已有素材，再用一次小范围新场景验收；本轮没有批准实施或产生新准确率结果。

| 候选 | 输入/模型 | 计数方式 | 回答的问题 |
|---|---|---|---|
| A | Apple Vision | 现有 Fox 规则，参数冻结 | 失败可否精确定位于获取、观测或规则 |
| B | Apple 姿态提取 | HumanBodyActionCounter | 时序计数能否减少对瞬时端点阈值的依赖；不是严格幅度计数的同义替代 |
| C | MediaPipe Full | 同一套 Fox 几何与计数规则 | 换关键点模型是否真正改善必要点覆盖和逐次事件 |

先在同一目标 iPad、同一图像序列、相同方向和明确采样时间基准上比较。A/B 尽量复用同一姿态序列；如格式映射无法保证等价，分别记录姿态前端，不将差异全归给计数器。不同模型置信度分别定义含义和门槛，计数规则及候选参数在独立验收前冻结。训练协调层的启动/中断测试与模型旁路分析都跑，旁路结果不能冒充整个流程通过。

测量至少包括：

- 准备成功率、准备耗时、为何取消/重置；始终失败也有记录。
- 必要关节连续可用的时段、缺失长度、明显跳变与主体错误关联。不同模型不以“置信度平均值更高”排名。
- 按人工标注的每次上举/返回匹配，分别计漏计、误计、合并和半程，不只比较总数。以用户参考为计数真值，不称为专业动作标准真值。
- 静止、换手、路人、短遮挡和离场的事件；丢失后恢复是否必须回屏操作。
- 首次输出等待、每次事件延迟、处理频率和端到端队列延迟；采样/降采样导致的窗口时间变化独立报告。

开发视频保留完整画面；随机拆帧不建立独立测试集。下一次正常使用可自愿保留短失败片段，用于新场景验收，不要求现在重录完整 A01/A02/A03 或额外负重运动。没有新图像时先完成旧素材实验，但停止宣称已解决现场泛化。

### 结果如何决定后续

- 必要关节稳定但 A 失效、B 有效：优先改善计数；B 若只会统计部分/无意图周期，不能代替最低幅度契约，可继续只作对照。
- 同帧 C 必要点和事件明显改善：评估体积、速度和维护后再替换姿态层，不重写训练资料。
- 正确点具备但因失锁/启动导致失败：先修 Fox 的产品与关联规则，不把它归因于硬件。
- 两模型都在某机位缺关键信息：先尝试用户可接受的一次机位调整；无法以自然动作解决则明确该动作/机位不支持。
- 建议最多两轮有明确假设的修正。若仍需小心配合才偶尔计数，就停止把视觉作为主线交付，保留人工记录，不继续无限调参。该轮数为项目范围建议，不是行业标准。

## 8. 深度和 3D 的位置

2D、模型推断 3D、硬件深度测量是三件事。Apple `VNDetectHumanBodyPose3DRequest` 不要求深度输入，有深度可帮助；官方还说明是 17 点或无结果，不能假设它一定改善半身缺点问题。[Apple 3D 姿态说明](https://developer.apple.com/documentation/vision/identifying-3d-human-body-poses-in-images)

以下是几何推断，不是本项目已测结论：深度可帮助可见表面前后位置，但同一视点仍看不到被完全遮挡的手腕或肘；模型只能结合先验推断。新增深度不是自动解决自遮挡、主体 lost 锁定或坏启动交互的办法。先定位具体失败，再决定是否值得独立深度实验；本轮不接 LiDAR、TrueDepth 或多设备。
