日期：2026-10-16。性质：产品方向记录，不是已实现界面或完整视觉定稿。本轮仅写文档，不改 App、不部署设备。

2026-10-17 UI 实践后共识：用户确认“最近记录为主，进行中的训练突出；训练之中专注于训练”。这是后续信息层级与卡片权重调整的依据，不要求训练执行页也变成卡片瀑布流。本次 0.6.0/build 15 先安装已完成 M1–M4 本地验收的候选，不在发布前临时重排首页，也未新增跨来源时间合流、日期分组或推荐排序。实际实现与真机安装情况见 [UI 候选发布记录](UI_RELEASE_0.6.0.zh-CN.md)。本页早期的“未实现”等描述保留为历史，不代表当前实现状态。

## 1. 本轮共识

Fox 是同一个生活助手 App，覆盖记录、健康感受、饮食、消费和训练，不按领域拆分多个 App。Home 以浏览内容为主，新增记录也采用卡片形式，不要求在“记录优先”和“浏览优先”之间二选一。

| 项目 | 当前方向 | 边界 |
|---|---|---|
| 首页形态 | 简单、纵向滚动的卡片瀑布流 | 不做唱片式翻阅、翻面或折叠卡堆 |
| 记录入口 | 一张可以输入文字、拍照的记录卡 | 不另放一个占满首页的聊天客户端 |
| iPhone | 一列卡片 | 当前工程仍为 iPad-only，手机适配尚未实施 |
| iPad | 两列、三列为主的探索方向 | 根据窗口宽度适配，窄分屏可退回一列 |
| 最小卡片 | 以 Home Screen 四个 App 图标所占的 2×2 区域作为体量参照 | 不是四个图标本体面积之和，不直接换算固定像素 |
| 外形 | 圆角矩形，整体遵循 Liquid Glass 设计语言 | 内容材质与控件材质区分，见第 5 节 |
| 内容 | 可逐步承载生活记录、昨天的训练回顾、明天的训练计划 | 不要求第一版把所有卡片做齐 |
| AI | 后续可在卡片上提供分析、讨论或提醒 | 不作为保存记录的前提，本轮不实现 |

本记录取代上一轮助手提出的“iPad 默认列表与详情并排、不推荐多列瀑布流”的建议；不能将那条建议继续当作已定稿方向。

## 2. 比例与尺寸：保留原意，不锁死百分比

用户描述：记录入口在 iPhone 约占 10%，iPad 约占 5%，并提出可以尝试“增大一倍”。

当前工作解释是：这些数字表达首页中记录入口的视觉/面积权重，不是记录行为的使用频率，也不是必须精确满足的屏幕面积公式。用户尚未明确比例分母，“增大一倍”指比例还是卡片实体尺寸也未定稿。草图应保留基准版与放大版供比较，不在实现中硬编码 10% / 5%。

最小卡片的 2×2 图标区域同样是体量类比，不复制系统桌面的固定行高。记录卡应至少容纳文字输入入口、拍照按钮和保存操作；触控、文字和键盘可用性优先于凑比例。进入编辑态时允许同一记录卡变高，不算引入折叠卡片系统。

“一列、两列、三列”暂按页面可见列数理解，而不是卡片必须横跨 1/2/3 个单元。跨列规则、最小列宽、卡片长宽比、圆角及内边距均待草图确认。仅有机型名称不足以决定列数，应以实际可用窗口宽度为准。

## 3. 瀑布流行为

确认采用可变高度卡片的普通瀑布流，不加入卡片堆、横向唱片浏览、拖拽排桌面或拟物翻页。卡片内容超过摘要容量时进入详情，不在卡片内部再放一个滚动页面。

后续原型需满足以下可用性约束：

- 记录卡容易找到；位置是否固定于首项待草图确认。不为了表达 5% 而把输入文字或拍照按钮缩到难用。
- 记录卡输入、拍照返回和保存期间不换列、不被新内容顶走、不因刷新丢掉草稿。
- 首次排布建立可解释的阅读顺序；同一数据在刷新、返回或设备旋转时保持身份和选中位置，避免跳到另一条记录。
- 多列不表示严格逐行时间顺序。每张事件卡片明确显示日期/时间；计划与已发生事件有文字区分，不能把“明天准备练”显示成“已经练了”。
- 图片预留尺寸再加载，使用可重建的显示缓存；不为排版裁掉或改写保存的原图。长文字、无图卡片、键盘、大字体和 VoiceOver 都参与验收。
- 不先上推荐算法、无限自动刷新或个性化排序。卡片排序和日期分组另行小范围确认，不因“瀑布流”一词自动引入内容推荐系统。

## 4. 记录卡与数据边界

第一版记录卡的核心是照片加文字，也允许纯文字或纯照片。文字可由系统键盘听写产生；Fox 不因此新增录音、ASR 或实时语音服务。

建议交互闭环：

```text
Home 记录卡
  -> 输入文字 / 拍照（可选）
  -> 保存
  -> 收到本机存储成功结果
  -> 出现可打开、更正的记录卡片
```

这是后续实现目标，不是当前 App 已支持的流程。`FoxJournalCore` 尚未接入 App，依赖与测试边界见 [记录与存储 v1](../journal/RECORD_STORAGE_V1.zh-CN.md)。

- 输入卡是操作界面，不是一条空的生活记录。未保存的输入不能当作正式记录展示。
- 保存以存储返回为准；失败保留草稿和照片并支持重试，不能清空后只显示“失败”。重试复用同一 `CaptureDraft` 的 ID、时间和内容。
- 存储只接收准备好的照片字节；未来界面层负责相机权限、有效图片处理和生命周期，不把媒体解码能力误当成核心库已具备。
- 默认显示“已存到本机”，不能显示尚未存在的“已同步”或“AI 已处理”。修改发生时间必须是显式行为，不把登记时间冒充起床或进食时间。
- 卡片是源数据的展示，不是每渲染一次就创建一条数据库记录。原始记录、训练回顾、计划和未来分析卡可有不同来源；它们不必共享同一业务 payload。
- 训练回顾与计划卡首先可投影现有训练数据，不要求 AI。训练 JSON 与通用记录库当前分开，后续需要展示适配，不偷偷迁移或重复落库。
- 在原始输入、用户确认事实和模型估计之间保留边界；卡片外观统一不表示它们的可信程度或证据来源相同。

## 5. Liquid Glass 的使用方式

用户确定的是圆角矩形卡片与 Liquid Glass 设计方向。以下是依据官方规范提出的材质分工，待原生预览确认，不将它夸大为已获验收的视觉稿。

Apple 把 Liquid Glass 定位于导航和控件层，并建议避免把它铺到普通内容层。[Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

因此建议：卡片内容使用清晰、可阅读的表面，导航、工具栏和关键操作优先采用系统 Liquid Glass 控件；不把所有照片、长文字和数字背后都做透明折射，也不叠加多层玻璃。圆角矩形与这一分工兼容，自定义圆角材质由官方 API 支持。[Applying Liquid Glass to custom views](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views)

使用系统支持的材质能力，具体 OS 可用性在实现时核验；不能因为库支持 iOS 16 就假定所有设备都有相同玻璃效果。旧系统保留同一信息结构并降级材质，不为新特效自动提高部署门槛。减少透明度、提高对比度、大字体及浅深色都需保留可读性。

## 6. 是否先做 Figma

建议先有本文，再做一份小型 Figma 布局探索；Figma 是可选设计工具，不是记录存储或原生预览的阻塞依赖。本轮没有创建 Figma 文件、连接账号、安装插件或选择付费方案。

下一轮设计材料建议限于以下范围：

1. iPhone 竖屏单列 Home；iPad 宽窗口两列/三列的对比及窄窗口退回一列。
2. 同一记录卡的空白、输入中、照片返回、保存中、失败保留、已保存状态，以及键盘出现后的布局。
3. 使用同一组示例内容比较约 10% / 5% 和放大版的视觉权重，示例须标为设计样本，不写入个人档案。
4. 展示记录卡、普通文字/图片卡、一个训练回顾和一个未来计划样例；不因此建立所有领域的组件全集。

不先做完整品牌系统、复杂动效、所有卡片类型或 Apple Watch 高保真稿。Figma 用于决定比例、层级和交互；真实玻璃、键盘、滚动和性能仍以 SwiftUI 原生预览及设备测试为准。

## 7. 下一次需要确认的少数问题

- 记录卡首屏常驻首项，还是允许在同一页其他固定位置出现？本轮只确定它也是卡片。
- 10% / 5% 具体按什么比较，“增大一倍”采用哪一种草图？不得为满足百分比损害输入可用性。
- 两列/三列的窗口断点，以及有无跨列卡片？在草图中看效果后再定，不从图标类比推导死尺寸。

卡片种类、排序和未来 AI 的详细交互逐步补充。跨设备同步、训练遥控、深度融合和分析计划统一进入 [后续任务台账](../planning/LIFE_LOG_BACKLOG.zh-CN.md)，本轮不实施。
