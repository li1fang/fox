# 给《面向 AI Agent 的约束驱动 UI 设计审查系统》作者的 Fox 实践反馈

反馈日期：2026-10-21，Asia/Bangkok。反馈批次：Fox-Practice-01。

对象：v0.1 概念方案。目的：描述一次项目内实践及随后真实使用暴露的问题，为作者准备正式 v0.2 提供输入；不是代写、发布或验收作者的 v0.2。

## 1. 可以先给作者的结论

我们在 Fox 原生 iPhone/iPad 应用中实践了“意图 -> 场景 -> 观测 -> 判断 -> 修改 -> 同条件复查”。这条路线有实际价值：它帮助发现卡片跨列跳动、长图虽完整显示却无法阅读、按钮检查通过但主要用时被裁切等问题，也形成了可复用的项目内审查入口。

但实践也表明，**一批静态场景通过，不代表页面在实际设备、真实入口和连续交互中可用；约束通过，也不等于产生了优秀的视觉设计。** 后续手机布局、横竖屏切换和持续姿态刷新中的选择器问题，正是首轮覆盖不足的反例。

因此，我们建议 v0.2 先把系统定位收敛为“有证据边界的轻量设计审查与迭代方法”，明确适用范围、动态状态和采集器可靠性，再考虑通用平台、自动打分或跨项目推广。该实践尚不能证明总体缺陷发现率、开发效率、成本或用户任务表现得到统计意义上的改善。

## 2. 实践对象与实施方式

Fox 同时存在两类明显不同的使用情境：首页随手记录与回看，训练页远看、少操作、专注当前动作。项目已有 SwiftUI、XCTest/XCUITest、本地记录及训练状态机，不适合为了接入浏览器工具重写成 Web。

我们没有先开发独立审查产品，也没有要求逐控件填写尺寸或约束语言。实际采取的是：

- 在 Markdown 中登记少量页面意图、来源、适用状态和观察方式。
- 用正式 View 注入隔离的合成数据、时钟、存储路径和相机 fixture，不另画一套截图专用界面。
- 通过既有模拟器与测试工具采集截图、可访问性树、元素 frame、窗口、键盘和源码指纹。
- 对已确认的不变量做确定性断言；层级、可读性和设计取舍由 Agent 结合截图判断，不使用 AI 总分自动放行。
- 保留失败批次，修改后新建结果目录；业务数据和状态语义由功能回归另行核对。

这是概念方法在单个项目中的轻量落地，不是已实现通用约束求解器、完整 SwiftUI 布局树提取、自动美学评价或跨平台审查服务。[S1][S2][S3]

## 3. 实践过程

主要实施与版本记录发生于 2026-10-17；本反馈于 2026-10-21 回读既有材料，没有重新运行应用、测试或设备。

| 阶段 | 实际工作 | 得到的结果与限制 |
|---|---|---|
| M0：建立理解 | 读取原方案、产品约束、正式源码；明确本地优先、记录与训练两种任务 | 用页面意图表启动，没有建立通用 DSL 或逐 Widget 标注系统 |
| M1：首页与记录卡 | 捕获双尺寸基线，调整输入卡权重、长图摘要和多列稳定性 | 输入增长触发跨列问题；修复 Layout 缓存后同条件复查。不是只检查最终一张图 |
| M2：详情与更正 | 调整正文/图片顺序、长图完整阅读、冲突恢复与文件面板流程 | 发现完整等比缩图不等于可读；功能回归还暴露旧面板关闭断言的假阳性 |
| M3：真实来源投影 | 首页展示本机计划、进行中训练和已确认回顾 | 不伪造排期，不为美观生成历史；打开卡片不能触发训练恢复写回 |
| M4：训练层级与审查入口 | 固定主要操作，弱化诊断，覆盖有限训练状态与字号/方向 | 几何断言通过后截图仍发现横屏用时裁切；宿主标识、键盘取证也出现误报 |
| 0.6.0：真机体验 | 同一候选安装并启动于既有 iPhone 与 iPad，核对原数据 | 安装与启动完成，不等于用户体验或相机可靠性通过 |
| 0.6.1：设备专属布局 | 根据用户反馈重新安排手机竖屏、横屏、常规/视觉训练 | 不再将 iPad 布局简单缩到 iPhone；用户确认手机竖屏符合预期、iPad 整体体验良好 |
| 0.6.2：动态交互补课 | 保留预览实例、去重方向配置、提升横屏快捷项；修复刷新中的设置选择 | 软件回归与安装有记录；真机启动当时受锁屏阻挡，实际旋转流畅度仍缺后续证据 |

M1–M4 是 UI 里程碑名称，不是 M4 芯片现场验收。模拟器实际使用 iPhone 17 Pro、iPad Pro 11-inch M5，不能冒充用户的 iPhone 13 Pro Max 与 M4 iPad。[S1][S4][S5][S6]

首轮场景目录有 36 个命名条件，实际还有输入前后的追加观测；这不是 36 个独立业务测试，更不是所有页面、设备、方向、字号和状态的完整组合。后续漏项说明，**场景数量不能代替覆盖范围说明**。[S2][S3]

## 4. 最有说明力的案例

### 4.1 两张图都合理，前后关系却错误

iPad 横屏输入增长后，一条既有记录的 x 从 16 变为 812，跨到另一列。单看输入前或输入后的截图，都可能觉得布局成立；实际违背的是输入时既有浏览位置保持稳定的项目约束。

修复为维护既有记录的列归属，并在 Layout 缓存更新时保留；改变列数时允许重新布局。失败与修复批次均保留。启示是：审查不应只覆盖状态截图，还要覆盖“某操作前后哪些关系必须保持”。这个项目选择不应被推广成所有瀑布流都禁止重排。[S1]

### 4.2 在边框内，不等于读得清

长图完整等比缩进固定高度框，几何没有越界，但实际变成一条很窄的图；手机训练横屏中，主要按钮都位于窗口内，计时数字却被内部短滚动区裁掉。

后一批 report.json 标为 Passed，本轮回看其截图仍能看到用时下半部不可见。原断言只验证了被选中的按钮，没有覆盖关键数字及其实际容器。随后分别调整长图阅读策略、紧凑计时区，并补对应信息断言。

建议明确区分：存在、位于窗口内、位于实际可见容器内、可点击、内容可辨读、完成任务。它们不能互相代替。完整阅读照片与首页摘要也不能使用相同的“必须完整显示”规则。[S1][S7]

### 4.3 审查器也可能污染被审查对象

外层就绪标识一度覆盖了子按钮的可访问性标识：截图有按钮，自动查询却找不到。另一次测试只看到系统面板背后的页面仍存在，就误判面板已关闭。还有一次把“切换每个输入框时软件键盘必须一直存在”设为前提，导致额外失败；实际焦点、输入值和保存流程需要分别核对。

这些不能全算产品缺陷，也不能一概归为“测试不稳定”后反复点击。我们分别修正了标识放置、关闭证据和取证时序，保留旧失败批次。建议把采集器/驱动故障与产品问题分开登记，并允许结论保持未知。[S1][S7]

### 4.4 排版正确，也可能表达了错误事实

计划卡不能因排版方便就写成“明天训练”；没有本机档案不能生成假的训练历史；已确认训练中的 partial 组，不能因为不属于 completed/skipped 而被显示成零活动。

此外，原训练仓库构造可能恢复并写回活动会话，不能直接拿来做首页只读展示。我们采用只读投影并独立验证打开卡片不写回。

这说明设计意图应包括真实来源、状态与副作用，而不仅是视觉结构。功能测试可以与设计审查共用驱动，但结论必须分开。[S1][S2]

### 4.5 首轮完成后，用户仍发现手机和视觉入口不可用

不能把首轮解释为“只改了首页，训练完全没做”：M4 确实整理了训练界面并覆盖有限状态。更准确的问题是，**那些场景不足以覆盖真实视觉入口、设备特有布局和所有关键方向。**

用户后来反馈平板视觉竖屏按钮越界、手机视觉内容过窄、常规训练仍需滑动才能看完主要信息。手机随后改为竖屏相机优先、横屏左控制右完整画面，标准字号下逐项验证动作、组次、目标、重量、用时和主要操作，而不是继续缩小平板布局。辅助功能大字号则明确允许次要信息滚动，不把所有情况都硬塞一屏。[S5]

也应区分既有约束漏测与用户后来明确的新取舍：避免越界、核心操作可用属于原有底线；横屏具体如何分配相机与控制区，是后续讨论明确的设计选择。不能把后来新增的全部要求都算成首轮漏检，也不能把所有漏项都解释成新需求。

### 4.6 静态布局之外，还有持续运行的界面

用户反馈旋转慢、没有过渡。正式 View 的宿主检查随后复现了旋转时预览 UIView 被更换；改为稳定槽位和按变化配置方向。它支持源码层面修复选择，但不是实测真机卡顿原因的完整证明。

设置面板选择不稳定也不是只改行距就解决：调整说明行后仍失败，继续处理持续姿态刷新对空闲设置交互的影响，关闭设置后恢复预览，计数中不停止或解锁状态。最终软件回归通过，实际真机旋转体验仍待观察。[S6]

这类相机、图表、流式文本和连续刷新的页面，需要“带更新的交互场景”，不能只注入一个静止对象后看截图。

## 5. 对作者正式 v0.2 的建议

以下优先级针对方法文档，不是要求 Fox 同时启动新功能。

### P0：明确审查对象和有效范围

最小审查单位建议写成：任务/入口 + 设备或窗口 + 方向/字号 + 业务状态 + 关键交互序列。它不要求穷举笛卡尔积，但每次结论要列明已覆盖、未覆盖，以及哪些条件没有实际观测。

例如“手机训练布局通过”过于宽泛；“标准字号、指定模拟器横屏、训练活动态，核心数字与暂停均在实际可见区域”才是有边界的结论。size class 相同也不自动意味着手机横屏应使用平板布局。

### P0：约束要有来源、作用域和冲突处理

建议至少区分用户已确认、业务不变量、项目选择、平台建议、Agent 假设。记录适用状态与允许的降级方式，不将 Agent 偏好升级为硬规则。

完整相机画面、大字号信息、首屏全部选项可能竞争同一空间。方法应要求提出取舍，例如保留主操作、次要设置进入二级，而不是统一缩字、裁画面或宣称“约束都满足”。不是所有页面都禁止滚动。

### P0：把证据与判断分开，把采集失败作为一等结果

截图、AX/几何、任务结果并列使用，不视为单向升级的证据等级。建议保留四类判断：明确约束违反、可用性风险、设计取舍、证据不足；再独立标注问题来源是产品、业务语义、驱动/采集器还是环境。

只有存在明确要求、可复现违反和可信断言时才自动阻止回归。可读性、可发现性或美学风险可以提出建议，不宜直接成为不稳定的 AI CI 红灯。系统还应能拒绝“选了某个测试，但实际没有生成其观测”的空通过。

### P1：从内容适配扩展到状态变化与连续刷新

建议把下列情况列为按风险选择的默认提示：输入增长前后、键盘/焦点切换、弹层打开/关闭、旋转、前后台恢复、持续数据刷新中的点击。只有起点和终点截图，不足以声称动画没有停顿、闪烁或重建。

静态页面无须为此都录性能轨迹；涉及过渡或卡顿的结论，再补最小过程证据。源码身份检查、模拟器 UI 流程与真机帧时间也要分别报告，不能拿自动化往返耗时代替渲染性能。

### P1：保留轻量实现，并用影响范围控制成本

优先复用正式 View、现有测试工具、少量合成场景和一个可浏览报告。采用隔离存储、显式 fixture 和正式资料不变检查，避免为展示效果修改用户记录。

每次页面变更先跑受影响分组及少量跨页面不变量；发布或共享布局调整时再扩大回归。失败先做最小复现，不循环重跑全套。不要求先有 Figma、通用 DSL、新 Agent 服务或第二套设计 App。

源码指纹有助于关联证据，但不是可恢复版本或完整环境快照。若未来承诺对外复现，需要另准备可恢复源码、环境和合成样本，不把 .tmp 目录当永久交付。

### P1：补充“比较设计”的步骤，不只“排除错误”

这是我们认为原方法最值得继续加强的部分。约束能发现明显退化，却不能单独决定构图、密度、留白、信息节奏或风格是否优秀。

建议在关键页面选择时，以同一内容提出两到三个有理由的候选，比较主要信息、操作成本、阅读路径和品牌一致性；明确选择理由，再用约束与回归排除退化。Figma 或原生预览均可作为比较媒介，不必先建立完整设计系统。

人类在少量重要取舍上给反馈，不必重复所有自动化操作。用户的“iPad整体良好”“手机竖屏符合预期”可以作为具体场景的定性反馈，不能扩张为全局、长期或统计性的 UX 提升。

### P2：用正常开发记录验证收益，再讨论平台化

目前证实的是能落地、能发现并复查具体问题。尚未证实比普通 Agent 看图更有效、缺陷召回更高、成本更低或维护量更少。

下一次正常页面修改可以分别记录场景准备、采集、判读、修复与维护成本，以及发现、驳回、接受取舍和仍未知的问题。没有独立问题真值集，不报召回率；没有用户任务观察，不报可用性分数；测试数和截图数不是设计质量指标。

跨项目、Web/原生适配和平台抽取应保持待验证，不因这个单项目成功落地就宣布通用。也不需要为证明方法另开一条大型基准或平台建设任务。

## 7. 本轮结论与后续复评

我们对方法的评价是：**方向成立，轻量落地有价值；静态检查的覆盖和可信度不能被高估，设计审查也不能取代设计选择。**

收到作者正式 v0.2 后，建议只核对：是否回应上述真实案例；是否避免将单项目发现外推成通用效果；是否给 Agent 一条小成本可执行的路径；是否明确运行时、工具故障、取舍和未知的处理。新主张若需要新证据，另选一次有限的正常产品修改验证，不追溯改写本轮结果，也不默认恢复 Fox 产品开发。
