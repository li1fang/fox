# Fox 约束驱动 UI 设计改进计划

日期：2026-10-17。路线 v0.1；M0 已完成，M1–M4 实现及本地候选验收完成。后续已按用户要求将 Fox 0.6.0/build 15 安装并启动于 iPhone 与 iPad，见 [发布记录](UI_RELEASE_0.6.0.zh-CN.md)。当前事实与失败/修正证据以 [M1–M4 实施记录](UI_M1_M4_EXECUTION.zh-CN.md) 为准；不是现场视觉可靠性或生产发布验收。

本文最初写于讨论阶段，当时没有改 App；随后用户授权连续实施。保留最初的目标、完成条件和范围，不用历史阶段声明代替当前状态。本轮候选尚未重新部署到真机，也不是生产发布。

## 1. 目标与决策

把用户的《面向 AI Agent 的约束驱动 UI 设计审查系统》作为待验证的方法，在 Fox 原生界面上逐步试行。每轮同时产生实际界面的改善和可复查的设计证据，不先做一个独立审查平台，再等待它服务产品。

两份附件正文的核心内容一致，已读取 DOCX 正文及表格，未对 Word 文档排版作视觉验收。来源为用户提供的 v0.1 概念方案，不是已验证的业界标准。附件识别值：

- Markdown SHA-256：`8f1d9d3494d3789615de578d4fb716adc4a3827470802d4f74b7c2a0135011de`。
- DOCX SHA-256：`e72cefb1cc54ee975412fdc5747d7c115a63867d1ce7211f36d35591541edf03`。

工作默认：先服务 Fox，验证有价值后再考虑跨项目复用。保留原生 SwiftUI 和既有自动化；Figma 可用于少量视觉取舍，不作为开工依赖。不会为接入 Storybook 等 Web 工具而重写原生 App，不新增 Agent 服务、MCP 服务或专用设计 App。

用户本轮调整：FIT-DIAG 不再安排专门的人工验收，不阻塞下一阶段。正常使用时再观察真实相机内容与额外负担；这不等于已经测过真人录像性能，更不把 FIT-LIVE 的计数可靠性改成通过。

## 2. 要保留的方法和要修正的假设

保留「意图 -> 场景 -> 观测 -> 分层判断 -> 修改 -> 同场景复查」。功能回归并行保留，不拿功能正确代替设计合理，也不拿好看的截图代替保存正确。

- 几何事实、规则来源和 Agent 判断分开。控件边框在屏内，不证明文字完整、图片易读或主要操作容易发现。
- 允许首页和详情滚动；训练中主要观测、当前任务和暂停操作应有优先权。支持范围内的小屏/大字体需要另定降级布局，不用缩小所有字体强行塞满。
- 「视觉完结错觉」作为风险假设，不按隐藏比例自动判错；用内容重要性、延续线索、任务路径和截图举证。
- 稀疏标注，只补源码无法表达的意图。Agent 推断标为推断，未获确认的取舍不升级为用户要求。
- 原生没有可直接套用的浏览器 DOM/CSS 观测协议。先用可访问性树、控件 frame 和少量 Debug 布局标记收集事实；不能观测的字体截断、遮挡或层级明确记为未知，再用截图核对。
- 不承诺恢复完整 SwiftUI 布局树，不承诺自动判断所有设计缺陷，不用 AI 总分宣布好用。

## 3. 当前 Fox 的源码基线

下列是本轮读源码发现的风险候选，不是新一轮渲染后已确认的问题。

| 区域 | 当前实现事实 | 要验证的设计问题 |
|---|---|---|
| Home 多列 | `FoxHomeView.swift` 最短列排布，按窗口宽度切换；手机或辅助功能大字号为单列 | 文字/图片/提示变化后是否跳位；多列阅读顺序是否清楚；照片多时是否影响浏览 |
| 记录卡 | 文字摘要最多 8 行，照片预览高 200 | 全文入口是否可发现；无图、长图、横图是否仍有恰当权重 |
| 记录详情 | 照片视图高 300，图像组件等比完整适配；正文位于照片之后 | 不裁图仍可能看不清细节；多照片是否把留言与发生时间推到难找的位置 |
| 输入 | 文字 2–5 行、缩略图横向排列，保存/错误与输入同卡 | 键盘出现、读取中、失败重试时，焦点、主要操作和输入上下文是否清楚 |
| 训练 | 自定义固定字号、部分固定尺寸，横屏右侧控制区可滚动 | 主次是否符合远看与少操作场景；暂停/结束是否需要翻找；诊断是否抢主任务 |
| 测试 | 已有 XCTest/XCUITest、合成姿态、故障注入与截图；Home 内部直接创建 Store | 功能测试很多，但设计场景不系统；应最小化拆分展示输入，使同一 View 可复现状态 |
| 支持范围 | `Info.plist` 仍有 `UIRequiresFullScreen=true` | 窄宽度组件预览不等于 App 已支持 iPad 分屏；不得在报告中混淆 |

已有卡片瀑布流、圆角矩形、原生控件材质方向沿用 [Home 设计记录](HOME_CARD_FEED_V0.zh-CN.md)。该文实施前段落作为历史，当前能力以源码和 [任务台账](../planning/LIFE_LOG_BACKLOG.zh-CN.md) 的后续实施记录为准。

## 4. 五个里程碑

### M0 设计意图与范围

本轮已完成源码盘点、附件对照和本路线文档，不包含新的界面实测或美学验收。

产出：项目级约束、页面任务优先级、首批场景建议、问题报告格式、非目标与台账映射。产品默认是同一 Fox、离线可记录、首页卡片浏览、训练期间少操作；不重新讨论是否改成聊天首页。

约束登记区分四类来源：用户已确认、存储/状态机已有行为、平台官方建议、待验证的设计假设。每条只需稳定 ID、意图、适用页面/状态、来源和验证方式；可从代码读取的尺寸不重复抄成第二套配置。暂不为每个 Widget 建元数据。

### M1 首页和记录卡的纵向试点

目标：先让一个真实页面的设计和审查方式一起改进，不仅搭工具。

实施顺序：捕获现状 -> 最小拆分展示输入 -> 接同一组件的场景数据 -> 采集事实与截图 -> 比较两种有限布局 -> 采用有依据的修改 -> 复查。字号、留白、图片体量、记录卡与浏览卡的主次均在此处理，不只查越界。

场景共享给 SwiftUI Preview 和 Debug 场景宿主；自动运行使用现有模拟器/XCTest 基础设施，不承诺命令行自动操作 Xcode Canvas。场景宿主必须隔离存储，不访问个人数据库、相册、真实相机或网络，不做一套与正式 App 不同的演示组件。

首轮建议控制在 12–16 个明确命名的场景，按风险挑选，不做维度笛卡尔积：空首页、少量混合记录、长留言、竖/横/长图、照片缺失、输入带键盘、读取中、保存失败、分页可继续。以 iPhone 竖屏和 iPad 横屏为基础，再定向加手机横屏、iPad 竖屏、大字号与浅深色。真实执行记录模拟器型号、系统、可用尺寸、字体及场景 ID，不把近似机型当真实 iPhone 13 Pro Max/M4。

完成条件：同一场景可重复生成，界面修改使用正式组件，主要状态具有可解释的层级与操作路径；明确越界/遮挡不遗留，设计取舍留理由。至少完成一次当前版与修改版的同条件比较；没有发现问题也如实记录，不为证明方法而制造缺陷。不要求所有内容一屏展示。

### M2 记录详情与更正流程

目标：把试点扩展到「找到记录 -> 看清照片和全文 -> 更正 -> 知道是否已保存」的任务路径。

处理长图/横图/多图的阅读策略，时间与原文的关系，摘要到详情的延续，以及更正、冲突、删除、备份等次要操作的层级。照片完整显示不等于内容可读；是否需要独立查看/缩放由场景对照决定，不预设全部缩成固定框。

补充场景：长文本配多图、照片加载失败、大字号及键盘、更正失败保留、修订冲突、备份取消。设计观测回答信息是否可见和可理解；已有功能测试继续回答字节、修订、重试和取消是否正确。无须另建存储或备份协议。

完成条件：主要任务和恢复入口可发现，图片及正文的策略清楚；已有记录/更正/备份回归通过，原始媒体和历史未因排版改变。系统相机、文件提供器的真实能力不由静态场景代验；不为本里程碑安排一套重复的人工逐按钮测试。

### M3 兑现 HOME-04 的只读训练卡

目标：用新方法交付台账中已经有价值、且不依赖 AI/同步的一项功能。

从本机训练档案读取当前可用计划、进行中训练和已确认回顾，形成 Home 的只读展示投影。用户看到计划与已完成记录的区别，可返回现有详情；不新建第二套训练状态，不复制成 `CaptureRecord`。

没有真实排期就不写「明天的训练」；默认计划要按真实来源标明，不能伪装成人工确认计划。自动次数和人工确认分开。手机没有 iPad 的历史就是空态，不为好看生成示例训练填充，也不因此启动设备同步。

完成条件：真实本机来源、空态和长内容场景均覆盖；打开/关闭卡片不修改训练档案，训练状态转换仍由原流程控制。与原记录卡的风格一致，但可辨识来源和状态。HOME-04 只有本阶段实际交付后才改为完成。

### M4 训练界面整理与日常审查流程

目标：把方法应用到更高约束的训练场景，同时把可复用的部分固定下来。

整理就位/等待识别、训练中、暂停、休息、反馈、总结及诊断核对的层级。区分训练模式与调试信息；优先保证当前动作/组次、观测次数/节奏和暂停，不把日志、参数和诊断资料塞进主视觉。核对后保留录像的语义不回退。

本阶段不改 Apple Vision、阈值、主体选择、计数算法、训练状态机或负重策略。不引入语音、数字人、实时 AI、深度或新动作；界面容易理解不等于现场计数已可靠。

完成条件：有限关键状态和支持窗口下完成设计复查，正式训练和诊断功能回归通过。输出一条可重复的本地设计审查入口，以及后续页面变更时使用的简短清单；只自动运行受影响场景，保留较小全局基线，不要求每次写代码全机型截图。

此时复盘是否值得跨项目抽取：若没有足够真实问题收益，或标注/维护成本大于收益，就保留轻量场景与报告，不升级为通用平台。

## 5. 审查证据与完成标准

一个问题至少包含：页面/组件、源码版本或本地变更标识、场景 ID、设备/窗口/字体/键盘条件、设计意图及来源、几何/语义/截图证据、判断类别、修正选择、复查结果和未观测项。可访问性树不是完整视觉布局，截图也不能单独证明业务正确。

| 输出类别 | 如何处理 |
|---|---|
| 明确约束违反 | 必须有已确认约束与复现证据；修复后重查同一场景，作为对应里程碑的阻塞项 |
| 可用性风险 | 提交上下文、可能代价及备选方案，不把 AI 猜测当作用户实测；通过修改或明确接受风险收口 |
| 设计取舍 | 说明竞争目标与推荐默认值，必要时展示少量 A/B；不能自动变成硬错误 |
| 证据不足 | 保持未知并注明缺什么观测，不按通过处理，也不强迫用户为每条未知专门测试 |

几何断言可与功能测试共用 XCTest 驱动，但输出与结论分开。明确规则可自动阻止回归；Agent 的风险/审美判断只出报告，不作为不稳定的自动 CI 红灯。未来若存在可靠规则再逐条升级，不先采购或搭建新的评审服务。

评价方法：记录已确认有价值的问题、被驳回的误报、待定项、人工审查耗时和附加维护量。没有完整人工真值时不报「发现率/召回率」；Agent 自报分数不算设计改善。沿用相同输入比较前后方案，必要时只请用户看少量视觉取舍，不要求用户重复已有自动化点击流。

静态视觉改动优先以模拟器和自动观测验收；需要真实触控、相机、传感器、系统提供器或实际性能证据时单独列出剩余范围，在正常使用中采集，不把所有功能统一挂到人工门槛上。

## 6. 推进规则与边界

按 M0 -> M1 -> M2 -> M3 -> M4 顺序推进。实施任务启动后，默认技术细节由 Agent 决定，已满足退出条件就进入下一阶段，不每个组件都询问。改变产品方向、引入收费/外发服务、扩展设备支持或改变数据/训练语义时才重新讨论。

初稿阶段边界（历史）：当时只做文档校验，没有开始 M1 的代码或自动化建设，也未升级 iPhone/iPad。随后实施已获授权；仍不默认推送 Git、启用新 CI 服务或宣布生产版本。

不启动 CON-01/02/03、INPUT-01、ANA-01/02/03、FIT-4 或 Part 2。对分析、同步等未来状态，只在确实需要讨论界面时用明确的设计样本，不实现隐藏后端、不展示虚假分析结果。

不新建第二套任务 JSON 或约束 DSL。项目约束及页面意图放在 `docs/design`，输入场景与测试就近维护在原生工程；发现与证据使用既有本地输出目录并避免个人素材入 Git。只有出现真实重复后才抽取共享观测代码或设计 token，避免先造完整组件框架。

本计划采用原生优先的可行基础：[SwiftUI Previews](https://developer.apple.com/documentation/swiftui/previews-in-xcode) 能复用实际 View 进行配置化预览；[Apple Scroll Views](https://developer.apple.com/design/human-interface-guidelines/scroll-views) 强调滚动延续的可发现性，并非一概禁止滚动。上述官方内容已读取，方法是否提高 Fox 的设计质量仍需 M1–M4 的实验证据。
