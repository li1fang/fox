# Fox AI 设计与回归效率调研报告

日期：2026-10-26，Asia/Bangkok。

本报告服务三个决定：怎样让 AI 帮 Fox 做出更好的设计，怎样处理折叠姿态，以及怎样显著缩短验证反馈周期。它不是约束驱动 UI 方法的 v0.3，不修改现有验收规则，也不启动悬停产品开发。

## 结论摘要

1. **先改善设计决策和验证结构，再增加工具。** Fox 已有正式 View 场景、约束、截图/AX 证据、确定性核心测试和回执，无需再造一个设计或测试平台。
2. **用户故事是正确方向，但应检查“理解、选择、执行、确认”，不只增加点击步骤。** AI 可以帮助发现问题、比较候选，不能把自己的评分当成人类可用性结论。
3. **原生 SwiftUI Preview 和现有场景应是主线。** Product Design 接通后已完成研究方法试用及本地模板核对，其移动原型模板是 React/Vite。随后核对的 Figma 插件有专门的 SwiftUI 双向转换指导，原生适配能力不能与 Web 模板混为一谈；但本轮未验证其转换质量、无损往返或实际提速。
4. **悬停上下分区有 Apple 官方依据，固定左右分区没有同等依据。** 应按可用区域、姿态和相机方向组织信息，保留普通 iPhone/iPad 的完整功能和训练状态。
5. **借鉴 Fitness+ 的专注与信息主次，不照搬课程平台。** Fox 必须另外表达视觉观测的可靠性、漏计修正、训练事实和诊断录像的保留状态。
6. **最迫切的工程改善是缩短错误定位路径。** 最近 Duo 批次可核对的 32 份运行合计 295.27 分钟，四次完整 public 尝试占 183.40 分钟；最终成功 public 的 52.06 分钟中，95.0% 是 iPad/iPhone UI 批次。不是所有测试都慢，也不是优先换插件或增加模拟器并发就能解决。

Fox 已经具备：

## 二、超过八小时的问题应怎样解释

### 2.1 本轮能核对的数值

统计范围严格限定为 `.tmp/verification/duo-m0-m1/*/suite.json`，按 `finishedAt - startedAt` 计算，不重新执行测试。它是最近的一轮实例，**不是此前全部 20 次 CI 的重新审计，也不能完整还原用户所说的八小时**。

| 范围 | 已记录时长 | 含义 |
| --- | ---: | --- |
| 32 份已结束运行 | 295.27 分钟 | 包括定向、预期失败、环境失败、取消与最终验收，不全是重复劳动 |
| 最早到最晚回执时间窗口 | 5 小时 36 分钟 | 不包括窗口外开发、等待、安装和云端排队；不能当人工投入 |
| 四次完整 public 尝试 | 183.40 分钟 | 17.88、65.73、47.72、52.06 分钟；最后一次通过 |
| 最终 public | 52.06 分钟 | 提交 `e5aeb88`，并非当前脏工作树的重新验收 |
| 其中 iPad UI | 40.17 分钟 | 52 个 XCTest 方法，部分方法内含多个场景 |
| 其中 iPhone UI | 9.30 分钟 | 25 个方法 |
| 最终 Duo 专项 | 6.16 分钟 | 同提交 11 项，另算，不冒充普通 public 覆盖 |
| 最终 public 的 design-review 类 | 17.21 分钟 | 9 个方法，含展示和真实交互，不能全部当作静态截图删除 |
| 最终 public 的 native-build 步骤 | 6.59 秒 | 已有缓存环境下的该步骤，不代表冷构建总成本 |

最终 public 与 Duo 合计约 58.22 分钟。前三次 public 已花费 131.34 分钟才到最后一次完整成功；这说明减少“昂贵阶段才发现已知类别的问题”有较大收益空间，**不表示这些失败当时都可以省略**。

核对了 `candidate-public-02`、`candidate-public-04`、`candidate-duo-04` 中记录的日志大小与 SHA-256，均与原日志一致。取消的 `candidate-public-03` 保留日志，但未完成步骤缺少最终日志摘要，相关分析仅使用其保留现场，不升格为完整验收。

### 2.2 失败发现与重复成本

| 已有证据 | 判断 | 下次怎样降低成本 |
| --- | --- | --- |
| 展开后仍上下排列的预期红测试 | 必要的需求验证 | 保留先失败测试；不必为它启动完整三设备回归 |
| 数字键盘弹层遮挡另一个输入框或保存按钮 | 有价值的真实交互环境发现，不能只凭最后截图说产品无问题 | 用一个完整输入故事覆盖打开、切换、关闭、保存，而不是每次只修一个命中点 |
| 旋转尚未完成便读 AX、报告行未滚入懒加载列表 | 测试前提/定位问题；需要修测试，不宜改产品迎合 | 把可见窗口、滚动容器、稳定渲染和焦点规则集中在既有 helper，先跑受影响路径 |
| 外盘生成物签名失败、预编译模块损坏、模拟器初始化退出 | 环境问题，不是动作算法或设计错误 | 小型预检先验证可写、构建产物和启动；失败后不立即扩大 UI 范围 |
| 适配器漏传 preflight、测试平台清单不匹配 | 可提前捕获的工具契约错误 | 宿主级契约检查应先于模拟器分配 |
| 每次测试修订替换候选后重跑完整 public/Duo | 符合当时正式规则，但成本很大 | 冻结前把受影响设备的定向故事收束；未来评估覆盖下沉，不能事后拼接旧绿结果 |

另一种耗时并非普通流程本身：`candidate-public-02` 的删除测试通过却用了 **980.061 秒**，下一候选同一方法为 **24.000 秒**；再下一处照片保存失败测试用了 **316.074 秒**。相应 iPad 日志分别有 17 次、12 次 `App animations complete notification not received`，最终成功批次为 0 次。异常跨不同测试出现，根因仍未知，不能断言是产品动画、用户收起窗口或内存中的任意一种原因。

用户随后明确：**八小时主要是机器和 Agent 持续运行，用户不必一直在场。** 因而主要痛点是开发反馈和收尾周期过长，不是缺少无人值守能力。较长的工具链迁移验证可能合理，但不宜成为普通布局修改的日常反馈方式。

仍需分开记录四种时间：Agent 判断与编辑、构建/测试执行、环境/排队等待、人需要配合的时间。优先衡量首次得到可行动反馈的时间、累计执行成本和从开始到结束的墙钟时间；有并行时不能直接把各步骤相加当墙钟时间。减少人工配合是保留目标，不是此次优化的主要收益指标。

### 2.3 一个新增的入口一致性风险

`scripts/design-review.mjs` 的 `run` 分支仍自行挑选已有模拟器并同步执行 `xcodebuild`，没有使用后来建立的共享模拟器会话；`LOCAL_UI_REVIEW.zh-CN.md` 也仍描述沿用已有实例。相对而言，`scripts/ipad.mjs` 的 UI 入口已经申请/核对 lease、隔离和释放设备。

这是源码静态核对发现的资源管理缺口，**不是八小时的已证实原因**。未来开展设计并行前，应让旧设计入口复用现有资源管理，避免两套入口争用同一台 Mac。本轮没有运行该入口或修改它。

## 三、设计插件到底能改善什么

OpenAI 将插件定义为可组合的工作指导、工具连接及其他扩展。安装多个插件不会自动建立统一设计规范或验收质量。[官方插件架构](https://developers.openai.com/plugins/concepts/plugins)

2026-10-26 首次查询目录，Figma、Product Design、tldraw、MagicPath、Canva、Webflow 均可发现，查询时未安装。随后系统先后确认用户已安装 Product Design 和 Figma。本次接续只读取本地工作指导、模板和官方资料，执行研究流程；没有调用 Figma 云端文件操作、建立画布或上传训练材料。安装及工具可用不等于已验证文件权限、套餐或设计转换。

| 工具或路径 | 对 Fox 的适用价值 | 局限与建议 |
| --- | --- | --- |
| SwiftUI Preview + 正式 View + 现有场景 | 原生布局、Dynamic Type、状态、系统控件语义能直接延续到产品 | 默认主线；Preview 不证明系统键盘、相机、持久化或现场可用性 |
| Product Design | 从 brief 出发比较流程、原型和交互概念；以来源和未知项约束研究 | 已进行研究方法试用；当前移动模板为 React/Vite 和模拟键盘，不等同于 SwiftUI、UIKit 键盘或 Duo 传感器验证 |
| Figma | 多候选并排、组件与排版审查；专门的 SwiftUI 双向语义转换指导，Code Connect 可关联既有组件 | 已核对指导与官方能力，未实测转换；应按需使用候选画布，避免同时维护全量画布与代码两份产品 |
| Visualize / tldraw | 故事分镜、流程和区域分配讨论 | 原型是讨论材料，不是原生验收。当前已有 Visualize，无须为画流程额外搭服务 |
| MagicPath | 交互原型和 Web 方向比较，目录描述可导出 React/TypeScript | 不能把 Web 导出当 Fox 原生实现；不建议为了用它改技术栈 |
| Canva / 图像生成 | 图标、展示图、视觉方向与宣传材料 | 不负责状态机、可访问性与真实操作质量，不是本轮瓶颈 |
| Webflow / Sites 等网站工具 | 独立网站与 Web 产品原型 | 不是当前 SwiftUI 训练界面的优先路径 |

Figma 官方合作说明支持把设计上下文交给 Codex，也支持从运行中的界面进入画布再迭代。但该说明不能证明 Fox 的 SwiftUI 能无损往返；Web 展示例子不应外推为所有原生控件和动画都自动还原。[Codex 与 Figma](https://developers.openai.com/blog/building-frontend-uis-with-codex-and-figma)

还有一个比泛用网页设计插件更贴近 Fox 的选项：Apple 的 Duo 准备指南提供 **app resizability skill**，可由 Xcode 使用或通过 `xcrun agent skills export` 导出给其他 Agent。官方同时说明它不能找出全部问题。建议以后作为只读审查补充，不盲目采纳生成修改；本轮未导出或安装。[Apple Duo 准备指南](https://developer.apple.com/iphone-duo/prepare/)

**插件试验的验收对象应是设计结果，而非生成速度。** 固定同一条训练故事、同一批合成状态、同一信息要求，比较“现有原生流程”和“一个插件辅助流程”。评估有用候选差异、被独立确认的问题、回到 SwiftUI 的改写劳动、人工解释量与后续维护成本。一项任务只能决定是否值得继续，不能证明长期总体优越。

### 接通后的研究方法试用

**范围：** Fox，面向当前个人训练者；围绕下一轮设计决策，选择“独立视觉页的一次弯举验证：准备、短暂丢点、恢复、核对、保留诊断”。使用本轮读到的正式源码、既有测试源码、用户反馈和官方研究资料。没有启动 App、浏览器原型或模拟器，没有采集本轮界面截图，因此这是流程研究与候选验收设计，**不是已经完成的 UI 审查或真人可用性测试**。

Product Design 的本地 `research` 工作流要求区分观察与推断、严重性与频率、产品摩擦与工具/环境问题。`audit` 工作流进一步要求访问当前实际流程、逐步采集并查看截图，不能用旧截图、代码或帮助页代替。当前插件没有已保存的产品上下文；本次直接使用 Fox 仓库，没有另建长期上下文或新的设计系统。公开依据沿用本文的 Apple/HAX 等一手材料，不检索同名 Fox 产品的投诉来替本项目背书。

本地 `templates/mobile-app/package.json` 和 `AGENTS.md` 显示，其移动模板使用 React DOM/Vite，并提供手机边框、模拟键盘、滚动、导航栈和底部面板。这适合比较流程和视觉方向，但不能复现 Fox 已经遇到的真实 iOS 数字键盘、XCTest 等待或相机生命周期问题。**插件的研究与审查方法可以直接复用；它的模板不应成为 Fox 必须维护的第二份产品。**

| 故事节点 | 当前源码/测试已经表达的保证 | 仍需回答的设计问题 | 最合适的下一份证据 |
| --- | --- | --- | --- |
| 选动作与手臂，点开始后退到机位 | `canCount` 不依赖当前全身可见；准备与倒计时有独立状态；已有退后入镜测试 | 用户是否知道可以先点击，再就位？等待与已开始是否容易区分？ | 正式 View 的准备/倒计时对照，加一次实际操作走查 |
| 第一轮动作中短暂看不清 | `qualityLabel` 区分短缺点、主体丢失、等待放低；计数与阶段独立 | 用户知道此刻该继续、放低还是重新就位吗？旧次数是否看起来被保留？ | 同一故事中三种恢复分支的状态与截图，不只截成功页 |
| 需要重新绑定主体 | 已有同一组保留前次计数的测试；独立视觉页也有专门测试 | 手持器材时需要靠近点击，会不会再次破坏机位？ | M2 自然采集与使用反馈；不能靠模拟器证明此操作轻松 |
| 结束并核对 | 原始自动数、修正数、人工参考数分开；未测得返回时长可保持缺失 | 用户是否知道自己正在修改什么，是否会把“未测得”理解成零或动作错误？ | 真实控件和合成边界数据的走查，结合存储不变量 |
| 决定保留或放弃录像 | 既有测试覆盖启动失败后保留、取消导出保留原件、弃录像不改变训练报告 | “保存报告”“保留录像”“导出文件”是否可区分，取消影响哪一项？ | 一个连续故事的状态反馈与持久化核对，不能只查按钮存在 |

表中依据来自 `VisionLabController.swift`、`VisionLabView.swift`、`FoxVisionUITests.swift`、`FoxDiagnosticUITests.swift` 和 `FoxWorkoutVisionUITests.swift` 的静态阅读。测试存在不代表本次重跑通过。正式训练与独立视觉验证是两个入口，不能把一边的测试当另一边的完整覆盖。

本次研究将风险收束为三项，而不是提出新的页面清单：

1. **恢复时该怎么做。** 若理解错误会中断整组训练，影响较高；已有历史反馈支持关注，但最近版本的出现频率未知，不能宣布仍有同样缺陷。下一步先比较当前提示与一个更明确的状态呈现，再用 M2 检验。
2. **核对与保存的对象。** 影响记录可信度；代码已有事实分离和反例测试，风险在理解而非“功能没做”。下一步检查一次连贯流程能否让人明确知道哪些数据留下了，不默认新增确认弹窗。
3. **节奏信息的证据边界。** 当前视图写明阈值区间与未评估项；应避免候选设计把局部阶段测量包装成完整动作质量。下一步比较信息主次，继续保留测量缺失和人工修正的原始含义。

**试用评价：** 工作流的证据纪律和问题分类适合 Fox，但与现有 EVIDENCE 约束已有较大重合。本次主要收益是把已有功能/测试映射到用户的理解任务，并识别模板的原生边界；没有独立 A/B、实际操作截图或耗时对照，不能归因宣称插件已提高设计质量、减少缺陷或缩短回归。它值得作为按需辅助，不值得仅因安装就迁移设计主线。

建议下一次真正的设计比较仍只选上述一条故事：以当前正式 View 为基线，生成少量有实际差异的候选，对照“用户看懂了什么、能否完成、错误能否恢复”。先记录需要澄清的信息，再决定 UI 是否要改。原生动态验证继续使用现有工具；插件原型通过不替代 Fox 的验收，也不要求为研究再跑全量回归。

### Figma 接通后的原生适配核对

Figma 本机插件 `16.0.0` 包含 `figma-swiftui` 及两个方向的指导，官方技能目录也列出了它。它不是只把网页改成手机宽度：指导涵盖 SwiftUI 布局与 Figma Auto Layout 的映射、系统语义色、SF Symbols、原生导航/表单及控件复用。这提高了它与 Fox 的相关性。[Figma 官方技能目录](https://help.figma.com/hc/en-us/articles/39166810751895-Figma-skills-for-MCP)

但“提供双向转换指导”不同于“有无损同步编译器”。本地指导明确将绑定、异步任务等运行时内容省略或表达为状态/注解；相机、计时、恢复和数据写入仍须保留原来的实现与测试。画布上正确的静态状态不能证明状态切换正确，也不能重现真实键盘与设备开合行为。本次未向 Figma 导入源码，未检验返回的 SwiftUI，不能宣布往返可用。

Code Connect 可以把设计组件与项目里的代码组件关联，让 Agent 获得实际组件引用、属性与使用信息；它不是全 App 自动同步。对 Fox 的潜在价值是减少“设计已有一种按钮，Agent 又重写一种按钮”的重复劳动。应先试一条故事，只有确实反复维护自定义组件时，再考虑映射，不能为了装好工具就先造组件库。[Code Connect 介绍](https://developers.figma.com/docs/code-connect/)、[MCP 组件集成](https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/)

还有一项维护风险：本地 `figma-code-connect` 指导仍写仅 Organization/Enterprise 可用，当前官网则列出 Professional 并说明席位和活动库/框架限制。**技能是执行参考，不是永远最新的产品事实。** 本次没有核对用户套餐，不要求购买或升级；将来真要启用映射，再核对实际权限和维护收益。此差异不应妨碍单纯的设计讨论，也不授权本轮建立映射。

建议的分工是：

| 环节 | 默认工具 | 明确产物与边界 |
| --- | --- | --- |
| 梳理目标、信息缺口和失败分支 | 既有文档 + Product Design 研究/审查方法 | 一条故事和待验证问题，不把 AI 意见当用户测试 |
| 对比布局与信息层级 | 优先正式 SwiftUI Preview；需要并排共同审阅时用 Figma | 当前基线加少量候选，不复制整个 App 或维护第二套运行逻辑 |
| 实现和验证 | SwiftUI + 现有核心/宿主/UI 测试 | 恢复、持久化、真实系统交互留在原生验收；画布通过不替代它们 |

未来若试 Figma，建议使用同一条“准备、恢复、核对保存”故事，带上来源提交、状态和窗口条件，只用合成内容。比较后将选中的改动回到正式 View；未采用的候选注明淘汰或过期，不承诺全仓库双向同步。验收看：是否帮助作出不同且更清楚的设计决定、是否复用了既有组件、回到原生的修订成本是否合理。八小时回归问题仍按第七节解决，不归因于缺少 Figma。

## 四、怎样让 AI 更好地参与设计

### 4.1 从故事出发，但不把故事写成给测试的答案

用户提出的方向与认知走查相近：逐步检查用户是否想得到这个结果、能否发现操作、能否理解操作与目标的关系、能否理解反馈并继续。经典方法也明确它是专家检查，不是真实用户测试。[Lewis 与 Rieman，任务中心设计第 4 章](https://hcibib.org/tcuid/chap-4.html)

这里需要两份互补内容，不必建立新文件格式：

- **用户故事**写目标、经验、姿态、看得见和摸得到什么，不预告按钮 ID 或正确答案。
- **检查脚本**由设计者列出真实动作及预期状态，再检查为什么用户能够找到并理解每一步。认知走查可以知道正确操作序列；只是不能因此把“测试会点”当成“用户会找”。

以 Fox 为例，先做一条完整故事及两个关键分支：

| 时刻 | 用户必须能够判断 | 行为/状态检查 |
| --- | --- | --- |
| 准备训练 | 当前动作、手臂、目标、机位是否合适 | 不需要先保持检测姿势才能触摸启动；已有状态是否清楚 |
| 退后站位 | 正在等待我还是已经倒计时 | 从真实入口开始，状态和取消入口一致 |
| 完成动作 | 当前次数是什么，节奏信息基于观测还是预设 | 数字、阶段与提示来源不混淆；远看是否可辨需要现场 |
| 暂时丢点 | 是否保留已完成次数，我该继续还是重新准备 | 保留/丢弃的事实明确，不把检测不确定显示成“你做错了” |
| 结束核对 | 自动计数与我的修正有什么区别 | 修正不覆盖原始视觉事实；未观察的返回时长保持缺失 |
| 保留录像 | 留在本机，还是已经导出给开发者 | 保存、导出、接收是不同状态；取消导出不丢已保留包 |

第二个分支是设备旋转/开合：训练、计数、输入和相机身份应怎样延续；不能只比较变化前后两张漂亮截图。先不用为每个分支都生成多套产品布局。

### 4.2 AI 的三个角色应分开

1. 设计者提出少量有真实差异的候选，而不是只换颜色。
2. 审查者先看目标、可见界面和操作结果，再看实现解释；分别报告约束违反、可用性风险、取舍与未知。
3. 确定性测试验证状态、数据、边界和交互。AI 的意见经复核后才转成必要断言。

这可以由同一工具不同上下文承担，不要求新建多 Agent 系统。另一模型或另一次对话也不等于独立真人研究；不能把多个 AI 同意当统计证据。

Apple 在 WWDC26 的原生原型指导中同样强调具体 brief、多个候选、真实感内容、边界状态和关键过渡，保留人的判断。对 Fox 的建议是每个重要取舍先比较 2–3 个方向，复用正式组件和命名 Preview，而非让 Agent 无限制生成页面。[Create UI prototypes using agents in Xcode](https://developer.apple.com/videos/play/wwdc2026/227/)

### 4.3 AI 审查不能单独成为通过门槛

2025 年的一项两 App 研究发现，模型能识别不少布局问题，但跨屏问题及某些控件/惯例识别仍较弱；另一项 30 个界面研究发现不同评价维度与人类偏好的一致性不相同。它们支持把 AI 用作早期筛查，不能给 Fox 当前模型背书，更不能据此宣称用户满意度或准确率。[Synthetic Heuristic Evaluation](https://arxiv.org/abs/2507.02306)、[MLLM as a UI Judge](https://arxiv.org/abs/2510.08783)

因此设计评判不设一个“美观 85 分就通过”的总分。目标应是减少已确认的信息缺口、错误操作和返工，保留成功与失败的过程证据。

## 五、Apple 对悬停到底建议了什么

### 5.1 官方指导与 Fox 推导分开

| 官方依据 | 对 Fox 的推导 |
| --- | --- |
| 悬停于桌面时，上方适合远距离观看，下方适合稳定触控 | 训练主要信息优先在面向人的区域；近手区域放调整与操作 |
| 避开活动折叠区域和相机区域；避免过度移动相关控件 | 计数、状态和主要操作不能被折痕拆散；不同姿态保持关系 |
| 不要求每一种姿态单独造一个界面 | 继续以可用区域和信息优先级适配，避免三套产品实现 |
| 姿态变化后保持功能和状态 | 小屏可进入二级，但不能丢失功能；开合不能重置训练 |
| 连续滚动的 feed 不应因为折叠被无谓搬动 | 最近记录保持连续浏览，不套训练的双区域编排 |

依据为 Apple 的 [Duo HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo) 与 [自适应布局 Tech Talk](https://developer.apple.com/videos/play/tech-talks/111463/)。这些是设计/技术指导，不应被写成“所有 App 必须把某个按钮放右侧，否则审核拒绝”的商店规定；本轮没有找到这种具体强制要求。

“有内屏摄像头的一半立起来”是 Fox 合理的目标摆位，不是从屏幕宽高就能推断的事实。也不应把平放一半描述成绝对不能显示浏览信息：用户靠近时仍可阅读重量、设置和操作结果；只是不能将训练中的关键提醒仅放在远看困难的平面上。

Fox 的未来悬停候选可按状态分配：

- 运动时：面向人的区域显示完整比例画面、次数、节奏和关键追踪状态；接近手的区域显示少量操作。
- 组间：靠近设备调整重量、休息和反馈；关键状态仍能远看。
- 核对时：回到适合阅读的整体布局，不强迫长报告永远塞在下半屏。

手持负重时，下方可触摸不代表适合频繁触摸。姿态只是布局输入，用户是否正在运动、距离与手是否空闲同样重要。

### 5.2 相机与布局不是同一项验收

Apple 提供虚拟前摄自动切换、相机方向协调与旋转协调机制。它们帮助知道相机相对显示的方向，不自动证明设备哪面实际落在桌上，更不能证明 Fox 的人物识别在不同镜头上同样准确。[Duo 相机指导](https://developer.apple.com/videos/play/tech-talks/111465/)

模拟器可核对区域布局、开合连续性和控件可达；实际取景、内屏镜头效果、远看文字、触摸导致机位晃动以及姿态识别可靠性仍需真机。在没有 Duo 真机时，不应把 M0/M1 的通过升级成“悬停已完美支持”。

当前 Fox 的 `CAMERA-FULL` 还要求等比完整显示且次数/状态不盖住图像。未来半透明节奏叠加属于明确的约束调整，应比较候选并更新来源，不能借本报告悄悄覆盖旧要求。

## 六、应该向 Apple Fitness 靠拢多少

### 6.1 借鉴训练的信息层级，不复制首页结构

Fitness+ 提供训练中的播放控制、可配置指标、时间呈现和音频提示；指标可以不显示而继续采集。这说明“保存什么”和“此刻展示什么”可以分离。[Fitness+ 训练内体验](https://support.apple.com/en-ng/guide/fitness-plus/apd12f665e17/ios)

适合 Fox 的部分是：主内容突出、数字少而清楚、次要控制渐进展示、训练前准备清楚、训练后回顾清楚、语音与视觉互补。Fox 首页仍应遵循已经确认的“最近记录为主”，不因借鉴 Fitness+ 就改成课程推荐首页。

不建议照搬活动环、热量竞赛或教练视频布局。Fox 当前的核心是本地记录和个人训练观测，不是课程订阅服务；视觉计数不等于能可靠估计热量，也不应以总分掩盖计数、节奏、动作质量的不同证据。

更适合 Fox 的定位是：**原生训练工具的清晰层级，加上可解释、可修正的视觉助手。** 当算法不确定时，用户应知道如何继续，而不是被漂亮的动画误导成系统仍在可靠计数。Microsoft HAX 的能力说明、恰当时机、纠正与不确定时降级可作为审查提示，不必引入其整套工具。[HAX 指导库](https://www.microsoft.com/en-us/haxtoolkit/library/)

### 6.2 Liquid Glass 不等于所有卡片都透明

Apple 将 Liquid Glass 主要用于控制和导航层；内容层应保持清楚的层级，避免玻璃叠玻璃和效果泛滥。因此，Fox 的圆角记录卡片可以保留，但不必全部玻璃化。相机背景变化大，次数、状态与文字对比应比材质表现优先，尤其要考虑降低透明度、提高对比度和大字号。[Apple Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

## 七、怎样实质减少回归时间

### 7.1 不必每次修改都完整跑三种设备

Apple 明确区分单元修改时的局部检查、集成时的目标测试和更广的多配置验证；也给出少量 PR 测试与完整后台测试的组织示例。[运行与解释测试](https://developer.apple.com/documentation/xcode/running-tests-and-interpreting-results)、[高效可靠测试](https://developer.apple.com/videos/play/wwdc2022/110361/)

Fox 已有分层入口，缺的不是再命名几层，而是把每层用途贯彻到实际开发。**以下为建议，现有 `verify:candidate` 的完整范围和 CI 触发本轮不变。**

| 修改或决策 | 日常反馈建议 | 候选交付建议 |
| --- | --- | --- |
| 调研、故事、纯文档 | 内容与链接检查 | 不因本文开启原生回归；若生成新发布候选仍遵守现有身份规则 |
| 布局函数、信息投影、策略 | 宿主单元/契约，必要的回放 | 相关集成覆盖；算法变化另验私有语料 |
| 单页原生设计 | 正式 View 预览/渲染 + 该页真实交互故事 | 保留受影响设备；共享组件触发跨形态检查 |
| 旋转、相机、导航、共享输入组件 | 三形态关键路径，不展开全部状态笛卡尔积 | 现行完整 public 与适用 Duo 专项 |
| 存储迁移、生命周期、工具链、共享训练控制器 | 边界反例及集中集成检查 | 扩大完整回归，不能只用截图替代 |

“共同核心测一次”只适用于纯逻辑；UIKit/SwiftUI 适配、键盘、方向、懒加载等平台行为仍需代表设备。新增 Duo 不应机械复制所有已有用例，也不能拿普通 iPhone 代替 Duo 的开合与预留区域。

### 7.2 优先级一：停止盲目的长跑循环

先利用已有失败分类、任务说明和回执，不增加系统：

1. 开始前列出本轮要得到的证据和最短入口，先查已有同提交结果。
2. 第一次失败保留现场，区分产品、测试、环境和未知；把假设与定向复现绑在一起。
3. 受影响的输入、旋转、报告故事通过后，再冻结候选。不要用完整 public 作为诊断的第一入口。
4. 同一未知问题在一个有界定向实验后仍未定位，转为补观测/报告阻塞，不能默默追加几个小时的全量循环。
5. 每次替代候选写明原因；需要的新完整验收照常执行，但先把已知相邻风险收束。

这部分主要是执行方式调整，已经有文档基础。没有理由要求用户为每一次正常排错都回复同意。

### 7.3 优先级二：优化 UI 检查的成本结构

需要小范围测试代码调整，而不是改训练功能：

- 从 17.21 分钟的设计审查类开始，逐项区分“静态展示”“真实输入/滚动”“持久化/完整流程”。纯展示尽量使用正式 View 的宿主渲染；交互保留 UI 测试。先验证新方式能捕获原有回归，不能直接删断言。
- 当前 `testHomeScenarios` 包含的若干场景又由 `testHomeSmokeScenarios` 执行；`training` 与独立旋转反馈亦有交集。smoke 是快速入口，完整套件不应无理由重复同一保证。更新 catalogue 和覆盖证明后再去重，不能只少跑一项就宣布优化。
- 当前多个方法内部循环场景并反复启动 App，某个方法慢时定位粒度粗。考虑按可独立验收的场景拆分，或在同宿主复用安全的展示状态；冷启动、清库和重启恢复测试不能合并掉。
- 为整条 XCTest 方法设置合理的执行时间上限并取得诊断，防止一次“通过”耗时 980 秒。Apple 的 execution time allowance 可帮助抓取挂起证据；它是防挂死工具，不是产品响应性能标准。[更快得到测试结果](https://developer.apple.com/videos/play/wwdc2020/10221/?time=704)
- 保留正常动画、中文键盘及真实触摸代表路径。不可为了测试快，全部禁用动画、绕过键盘或调用内部保存函数，从而漏掉此前真实发现的问题。
- 统一旧 `design:review` 的会话管理，使用已存在的运行器/所有权机制，不另建模拟器管理器。

原生入口目前使用 `xcodebuild test`，没有显式拆成 build-for-testing/test-without-building。可以以后评估同候选构建复用，但最终成功批次的 build 步骤已很短，**这一项不应优先于 UI 等待、场景重复和失败定位**。构建缓存只节省构建，不等于复用测试通过。

### 7.4 优先级三：有证据后才改变正式 CI 策略

当前 CI 先跑 `native-ui-probe`，然后 `public-native` 又覆盖相关场景；它有提前暴露历史不稳定用例的意义，也付出重复成本。不能仅看重复就删除。待 probe 稳定性与节省的失败发现时间可度量，再讨论合并执行、共享同候选构建，或调整 PR/发布的测试计划。

若未来允许改变触发，可评估“快速 PR 门禁 + 指定候选/定时完整回归”。这是明确的质量策略选择，不是 Apple 文档自动授权，也不在本轮实施。私人媒体仍不进入公开云端。

本机实核为 M1、16 GiB 内存。首先继续一台活动模拟器、串行原生批次；不要用三台并发换来交换内存和偶发超时。把独立 Web/核心工作移到合适执行环境、或采用独立 Mac runner，比同机强并发更可取，但需另外测量传输、排队与维护成本。iPad 不等价于 Mac 的 Xcode/XCTest 执行宿主，不因它算力更强就迁走全部回归。

### 7.5 建议的成功标准

以下是待讨论目标，不是已经达到的速度承诺：

- 日常受影响路径在温缓存条件下尽量 5–10 分钟反馈；纯核心和文档更短。
- 同一未知失败不无依据重跑完整套件；每一次新运行都对应新修复、明确假设或有界可靠性测量。
- 先把一轮修改控制为定向收束后通常一次冻结完整验收；发现新问题仍应替换候选，不能为完成次数指标掩盖失败。
- 当前正常 public + Duo 的约 58 分钟作为实测起点。先减少多次完整重跑，再尝试将保留等价保证的完整本地验证降到约 40–45 分钟；不能预先承诺八小时变几分钟。
- 用同一源码候选、相同输入/配置和注明的冷暖缓存比较执行器，不用复杂度不同的任务总时长冒充因果提速。流程收益另记录完整启动次数、未定位重跑、人类配合次数与逃逸缺陷。
- 确保已知回归仍能被检出：裁切、输入丢失、错误保存、计数重置、报告行不可达、缺失返回时长被补造。必要时用受控故障注入证明检查有效。

可以把“同条件累计测试成本减半”作为改进方向，但只有下一次对照评测才知道实际收益。少量任务不宜报告稳定的 P95 或长期缺陷率。

## 八、设计与数据采集怎样并行

可以并行，但并行对象应是“稳定版本采集”与“设计研究/候选原型”，不是两边同时修改同一版本：

1. 当前设备保持采集版本，不更新签名、不推送 UI、不改变相机算法与记录格式。
2. 设计工作使用合成内容、已有截图和独立候选；不占用正在采集的 iPad，不启动实时同步。
3. 每份新数据保留版本、动作、机位、原始视频/6DoF 时间来源。设计候选与算法评测结果分别记录。
4. 新设计进入产品前，再执行受影响自动化和必要真机体验，不把原型评判当安装版验收。

这也保留实验可解释性：不能在测试动作识别时同时变更启动交互、摄像头预览、倒计时和采样策略，然后无法判断改善来自哪里。

## 九、还应回答的问题

| 问题 | 建议的初步立场 |
| --- | --- |
| 八小时主要是哪种成本？ | 用户已确认主要为机器和 Agent 持续运行，不需一直在场；优先缩短反馈和收尾周期，保留无人值守能力 |
| 设计成功是更美，还是更容易完成训练？ | 两者都需要；首先保证信息足够、错误可恢复，再比较视觉方向 |
| 相机画面、数字、节奏谁优先？ | 准备时取景优先，运动时次数/节奏/状态优先级上升；是否调整完整画面约束需明确讨论 |
| 要不要每种姿态一套 UI？ | 不要。共用信息与行为，按区域组合；仅有明确任务差异才增加布局模式 |
| 无法计数时应该怎样继续？ | 这是产品体验核心，不是只有成功态的设计附注；保留事实，允许修正或手动继续 |
| 自动化通过是否意味着训练时能看懂？ | 不意味着；距离、光线、身体姿态、疲劳和双手占用仍需真实使用 |
| 首先买工具/设备还是改善流程？ | 先处理已观测的测试结构和入口漂移；购买/迁移需要成本对照，不凭“大模型更强”推断收益 |
| 怎样防止框架开发压过 Fox 产品？ | 只围绕下一条真实故事改现有工具；用更少返工和等待衡量，而非文档/插件/测试数量 |

## 十、推荐讨论顺序

**第一优先：验证效率与入口一致性。** 它决定后续每项 UI 或视觉开发的成本。建议下一轮只明确一个范围：回执耗时拆分、设计入口接入已有会话、静态与交互检查分开、异常长方法有界诊断；正式 CI 策略另议。

**同步进行：一条视觉训练故事的设计比较。** 用既有原生 Preview 作为基线；若要试插件，只加入一个辅助路径，不同时迁移到 Figma 和另一套原型平台。先解决准备、理解追踪状态、结束核对的衔接，不在数据采集时替换设备版本。

**后续：有新样本后推进视觉分析；悬停保持候选设计。** 无 Duo 真机的部分继续标明边界。方法文档是否升级，由这些实践产生的证据决定，而不是先为 v0.3 寻找内容。

本报告及接续补充只修改此调研文档；没有改 App、算法、测试选择、CI、现有方法稿或设备，没有执行原生回归。用户已安装 Product Design 和 Figma，本次使用前者的本地研究工作流并核对两者的指导/模板及官方资料；未构建原型、建立云端文件、上传材料或发布设计。目录检查只用于核对本报告和原有文件保留，不代表新软件验收。
