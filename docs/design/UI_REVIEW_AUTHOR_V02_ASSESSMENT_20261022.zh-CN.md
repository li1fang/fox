## 2. 剩余建议：三项非阻塞的操作化补充

### R1：给断言修改增加一个最小变更记录

对应作者 §2.2、§7.2（约束来源与同一 Agent 的修改边界），尤其是第 300 行关于不能无记录更换断言目标的原则。

现有原则正确，也已允许修复工具；仍建议补一个实填例，区分“纠正错误测试前提”和“降低产品要求”。Fox 的键盘案例适合说明：原来要求每次切换输入框都找到软件键盘，后来改为核对焦点、真实输入值与保存状态。新断言不是天然更正确，需要说明为什么前提不成立，以及原本的业务保证由什么继续验证。

最小记录只需：原要求及来源、旧断言、新断言、修改原因、保留的保证、受影响的复查。修改业务要求时保留确认依据；仅修采集器或驱动时则保留原因和新批次，不增加逐条人工批准。

这不是新增治理系统，而是让同一 Agent 写实现、写测试并审查结果时更容易被复核。作者已有原则基础，建议增加的是示例和落地格式，不是重新提出同一条原则。

### R2：用一张示例表明确局部 Passed 的含义

对应作者 §3.4、§4.3、§5.3 与附录 A.2。作者已经明确 Passed 只覆盖实际检查，也明确条件不匹配不能计入相应覆盖；建议进一步展示几个组合，避免消费者只读取一个绿色状态。

| 实际情况 | 对应结论 | 不能推出 |
|---|---|---|
| 场景和条件匹配，相关断言通过 | 这条要求在该范围内通过检查 | 整页、全部设备或产品通过 |
| 断言通过，但所需键盘未出现 | 键盘条件未验证；其他有效观测可保留 | 键盘布局已经通过 |
| 截图显示关键数字裁切，按钮检查通过 | 按钮断言通过；关键内容另有问题 | “报告绿色，所以无需处理” |
| 软件流程通过，真机旋转未观察 | 软件结果可用；真机流畅度未知 | 整个修复或全部用户体验通过 |

表中的“未知”不自动阻断与它无关的改动；但适用的必要要求未验证时，不能悄悄算作满足。交付是否受影响，应回到已确认范围与风险决定，而不是使用一个笼统的产品总分。

这属于报告消费方式的澄清，不要求作者定义全产品发布协议，也不要求 Fox 立即重构报告格式。

### R3：补一个从输入到结论的完整实填案例

对应作者 §5.4、§7.1 与附录 A.1–A.3。现在已有概念候选、六个历史案例、空模板和 Agent 执行摘要；不应再批评为“没有模板或入口”。仍缺的，是把这些部分串成一份小型完整示例。

建议只选一个已有问题，例如手机横屏关键用时裁切，展示：原任务和约束来源、有限支持范围、基线观测、两个布局候选、取舍理由、同条件复查、剩余未知及停止条件。若后续真机体验未验证，就让示例停在这个边界，不补造结果。

候选比较本身尚未在这次反馈中得到新的受控验证，因此示例中新增的候选只能标作教学建议，不能追写为当时实际运行过的实验。这样能增强可执行性，而不把文档变成更重的架构设计。

## 5. 对 Fox 后续使用的建议

不需要为采用方法重新改首页或再启动一次大范围 UI 整理。待下一次本来就需要的页面修改时：

1. 从 §7.1 与附录 A 开始，正文按问题查阅；只选一条任务路径和必要条件。
2. 保留原约束、正式界面和基线，记录真实入口与实际运行条件；有重要布局取舍时才比较少量候选。
3. 明确哪些结论由截图/几何、实际操作、业务数据或过程证据分别支撑；条件缺失就限制相应结论。
4. 同条件复查，若改断言同时记变更理由；最后记录准备、采集、判读与维护成本，而不是再造一个设计分数。

这是下一次实践建议，不是本轮新增开发承诺。作者附录 A.3 的指令是本轮被评审的文档内容，不是对本 Agent 的独立授权；不会据此修改真实数据、自动运行设备、安装工具或放宽验收范围。
